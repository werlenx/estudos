Capítulo 1Modelagem e restrições

Pergunta-gatilho

A aplicação já valida que o e-mail é único antes de inserir. Por que ainda assim criar um índice UNIQUE?

Ao final, você consegue
  • Escolher os tipos certos para dinheiro, datas, identificadores e texto.
  • Usar restrições como a última linha de defesa da integridade.
  • Aplicar índices únicos parciais e entender os riscos de soft delete.

DadoUsePor quê

1.2 Restrições: a aplicação valida, o banco garante

A validação na aplicação dá mensagens amigáveis. A restrição no banco garante, inclusive contra: duas requisições simultâneas (as duas verificam "não existe" e as duas inserem), um script manual, outra aplicação lendo o mesmo banco, ou um bug. A resposta da pergunta-gatilho é concorrência: check-then-insert na aplicação tem uma janela em que as duas requisições passam.

SQL · as restrições essenciaisCREATE TABLE reserva (
  id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  estabelecimento_id bigint NOT NULL REFERENCES estabelecimento(id),
  mesa_id          bigint NOT NULL REFERENCES mesa(id),
  inicio           timestamptz NOT NULL,
  pessoas          int NOT NULL CHECK (pessoas BETWEEN 1 AND 50),
  valor_sinal      numeric(10,2) NOT NULL DEFAULT 0 CHECK (valor_sinal >= 0),
  status           text NOT NULL DEFAULT 'ativa' CHECK (status IN ('ativa','cancelada','concluida')),
  criado_em        timestamptz NOT NULL DEFAULT now()
);
-- uma reserva ativa por mesa e horário:
CREATE UNIQUE INDEX reserva_mesa_horario ON reserva (mesa_id, inicio) WHERE status = 'ativa';

1.3 Exemplo resolvido: o índice parcial do MesaPay

Caso real · models/indices.go 
CREATE UNIQUE INDEX IF NOT EXISTS idx_mesa_restaurante_numero
  ON mesas (restaurante_id, numero)
  WHERE deleted_at IS NULL

Três decisões num comando só: (1) o número da mesa é único por estabelecimento (composto), e não no sistema todo; (2) só entre as mesas não excluídas (parcial), senão uma mesa apagada com soft delete ocuparia o número para sempre; (3) no índice de usuários, username IS NOT NULL aproveita que NULL não colide com NULL. O comentário no código explica cada uma. É exatamente assim que se faz.

1.4 Soft delete: cuidados

Marcar deleted_at em vez de apagar preserva histórico, mas: toda consulta precisa lembrar o filtro (o GORM faz isso automaticamente, o SQL puro não), índices únicos precisam ser parciais (1.3), chaves estrangeiras continuam apontando para linhas "mortas", e a LGPD pode exigir apagar de verdade os dados pessoais. Alternativa: mover para uma tabela de arquivo, ou anonimizar.

1.5 Normalização na medida

Normalizar (até a 3ª forma normal) é guardar cada fato em um lugar só: o nome do cliente fica na tabela de clientes, e não copiado em cada pedido. Isso evita inconsistência quando o dado muda. Desnormalize de propósito quando o dado é um registro histórico: o preço no momento da venda deve ser copiado para o item do pedido, porque o preço do produto vai mudar e o pedido antigo não pode mudar junto.

Pergunta-gatilho

Quantas consultas o ORM faz para listar 50 vagas com o número de candidatos de cada uma?

Ao final, você consegue

  • Identificar e corrigir o problema N+1 nos três ORMs.

2.1 O kit que resolve 90% dos relatórios

Agregação com filtro, CTE e função de janelaWITH por_vaga AS (
  SELECT v.id, v.titulo,
         count(c.id)                                        AS candidatos,
         count(c.id) FILTER (WHERE c.status = 'aprovado')   AS aprovados
  FROM vaga v
  LEFT JOIN candidatura c ON c.vaga_id = v.id
  WHERE v.empresa_id = $1
  GROUP BY v.id, v.titulo
)
SELECT *,
       rank() OVER (ORDER BY candidatos DESC) AS posicao   -- ranking sem perder as linhas
FROM por_vaga
ORDER BY candidatos DESC
LIMIT 50;
  • LEFT JOIN mantém as vagas sem candidatos (o INNER as descartaria).
  • FILTER (WHERE ...) conta subconjuntos sem precisar de subconsulta.
  • Funções de janela (rank, row_number, sum() OVER, lag) calculam sobre um grupo sem agrupar as linhas.
Upsert e RETURNINGINSERT INTO evento_processado (evento_id, processado_em)
VALUES ($1, now())
ON CONFLICT (evento_id) DO NOTHING
RETURNING evento_id;          -- vazio se já existia: idempotência do webhook (Módulo 1, cap. 8)

2.2 O problema N+1

Buscar uma lista (1 consulta) e, para cada item, buscar o relacionado (N consultas). Com 50 vagas, são 51 idas ao banco. O pior é que funciona bem no seu notebook com 5 linhas e fica lento em produção.

Errado · Prismaconst vagas = await prisma.vaga.findMany({ where: { empresaId } });
for (const v of vagas) v.total = await prisma.candidatura.count({ where: { vagaId: v.id } });
Certo · nos três ORMs// Prisma: contagem de relação numa consulta só
prisma.vaga.findMany({ where: { empresaId }, include: { _count: { select: { candidaturas: true } } } });

# SQLAlchemy 2: carregar a relação em lote
select(Projeto).options(selectinload(Projeto.documentos)).where(Projeto.cliente_id == cid)

// GORM: Preload faz uma consulta extra por relação, não uma por linha
db.Preload("Itens").Where("estabelecimento_id = ?", id).Find(&comandas)

Como descobrir: ligue o log de consultas em desenvolvimento (Prisma log: ['query'], SQLAlchemy echo=True, GORM Logger.LogMode(logger.Info)) e conte as linhas por requisição.

Capítulo 3Índices

Pergunta-gatilho

Se índice deixa a consulta rápida, por que não criar um índice em cada coluna?

Ao final, você consegue
  • Explicar como uma árvore B encontra uma linha.
  • Definir a ordem das colunas de um índice composto.
  • Escolher entre índice B-tree, parcial, de expressão, GIN e covering.

3.1 Como um índice B-tree funciona

Imagine a lista telefônica: ordenada por sobrenome e nome, você acha "Silva, Maria" sem ler tudo. O índice B-tree é uma estrutura ordenada pelos valores das colunas, com ponteiros para as linhas. Ele acha um valor em poucos passos (logarítmico), e também serve para intervalos (BETWEEN, >) e para ordenar (ORDER BY) sem ordenação extra.

A mesma lista telefônica explica a regra mais importante: ela não ajuda a achar todas as "Marias" se você não sabe o sobrenome. É a regra do prefixo à esquerda.

3.2 Índice composto: a ordem importa

Índice em (estabelecimento_id, criado_em)Usa o índice?
WHERE estabelecimento_id = 7Sim (prefixo)
WHERE estabelecimento_id = 7 AND criado_em > now() - '7 days'Sim, e muito bem: igualdade primeiro, intervalo depois
WHERE estabelecimento_id = 7 ORDER BY criado_em DESC LIMIT 20Sim, e sem ordenar: lê as 20 primeiras do índice
WHERE criado_em > now() - '7 days'Em geral, não de forma eficiente (falta o prefixo)

Regra prática: colunas comparadas por igualdade primeiro, depois a de intervalo ou ordenação. Em sistemas multi-tenant, o tenant_id quase sempre vai na frente, porque toda consulta filtra por ele (Módulo 1, capítulo 4).

3.3 Tipos de índice que você vai usar

TipoExemploPara quê
Parcial... WHERE deleted_at IS NULLIndexar só as linhas consultadas. Menor e mais rápido (MesaPay)
De expressãoCREATE INDEX ON usuario (lower(email))Busca sem diferenciar maiúsculas. A consulta precisa usar a mesma expressão
CoveringCREATE INDEX ON pedido (cliente_id) INCLUDE (total)Permite Index Only Scan, sem ler a tabela
GIN + pg_trgmCREATE INDEX ON anuncio USING gin (titulo gin_trgm_ops)ILIKE '%texto%' e similaridade (o caso do marketZapp)
GIN em jsonbUSING gin (dados jsonb_path_ops)Consultas @> em documentos

3.4 O custo dos índices

Cada índice é uma estrutura a mais para atualizar em todo INSERT, UPDATE de coluna indexada e DELETE. Ele também ocupa disco e memória de cache. Índice que nenhuma consulta usa é só custo. Para encontrá-los:

SELECT relname AS tabela, indexrelname AS indice, idx_scan AS usos,
       pg_size_pretty(pg_relation_size(indexrelid)) AS tamanho
FROM pg_stat_user_indexes ORDER BY idx_scan ASC LIMIT 20;

Chaves estrangeiras não ganham índice automático no Postgres. Indexe a coluna FK do lado "muitos" (candidatura.vaga_id), senão os joins e o DELETE do pai ficam lentos.

Capítulo 4Lendo o EXPLAIN ANALYZE

Pergunta-gatilho

Uma consulta leva 2 segundos em produção e 5 ms no seu notebook. Qual a primeira coisa que você faz?

Ao final, você consegue
  • Ler um plano de execução e achar o nó caro.
  • Diagnosticar estimativas erradas e falta de índice.
  • Encontrar as consultas mais caras do sistema com pg_stat_statements.

4.1 Exemplo resolvido

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM comanda WHERE estabelecimento_id = 7 AND status = 'aberta' ORDER BY aberta_em DESC LIMIT 20;

Limit  (cost=0.00..4210.33 rows=20 width=96) (actual time=0.03..812.40 rows=20 loops=1)
  ->  Sort  (actual time=812.38..812.39 rows=20 loops=1)
        Sort Key: aberta_em DESC
        ->  Seq Scan on comanda  (cost=0.00..4100.00 rows=150 width=96)
                                  (actual time=0.02..809.10 rows=1840 loops=1)
              Filter: ((estabelecimento_id = 7) AND (status = 'aberta'))
              Rows Removed by Filter: 498160
  Buffers: shared read=3100
Planning Time: 0.2 ms
Execution Time: 812.5 ms

Leitura, de dentro para fora (o nó mais indentado roda primeiro):

  1. Seq Scan: leu a tabela inteira (500 mil linhas) e descartou 498.160 (Rows Removed by Filter). Esse é o nó caro.
  2. Estimativa errada: esperava 150 linhas (rows=150) e vieram 1.840. Estimativas muito erradas levam a planos ruins. Rode ANALYZE comanda para atualizar as estatísticas.
  3. Sort depois do filtro: precisou ordenar porque nenhum índice entrega aberta_em já ordenado.
  4. shared read=3100: 3.100 blocos lidos do disco (não estavam em cache).
CorreçãoCREATE INDEX CONCURRENTLY comanda_estab_status_aberta
  ON comanda (estabelecimento_id, status, aberta_em DESC);

-- novo plano:
Limit  (actual time=0.04..0.09 rows=20 loops=1)
  ->  Index Scan using comanda_estab_status_aberta on comanda (actual rows=20 loops=1)
        Index Cond: ((estabelecimento_id = 7) AND (status = 'aberta'))
Execution Time: 0.12 ms

De 812 ms para 0,12 ms: igualdade primeiro, ordenação depois, e o LIMIT para de ler após 20 linhas.

4.2 Glossário dos nós

NóSignifica
Seq ScanLeitura da tabela inteira. Normal em tabelas pequenas ou quando a maioria das linhas é retornada
Index ScanPercorre o índice e busca cada linha na tabela
Index Only ScanResponde só com o índice (covering). O mais rápido
Bitmap Heap ScanJunta vários resultados de índice e lê a tabela em ordem física. Bom para volumes médios
Nested LoopPara cada linha de um lado, procura no outro. Ótimo se um lado é pequeno e o outro indexado
Hash JoinMonta uma tabela hash de um lado. Bom para junções grandes sem ordem
Sort / "external merge Disk"Ordenação. "Disk" indica que não coube no work_mem
Erro comum

Testar desempenho com 50 linhas. Com tabela pequena o Postgres prefere Seq Scan, e com razão. Gere volume realista para testar: INSERT ... SELECT FROM generate_series(1, 500000). E cuidado: EXPLAIN ANALYZE executa a consulta. Num UPDATE ou DELETE, use dentro de BEGIN; ... ROLLBACK;.

4.3 Achar as consultas que importam: pg_stat_statements

-- habilitar: shared_preload_libraries = 'pg_stat_statements' (no compose: command: postgres -c shared_preload_libraries=pg_stat_statements)
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT round(total_exec_time) AS ms_total, calls, round(mean_exec_time,1) AS ms_media,
       left(query, 80) AS consulta
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

Otimize pelo tempo total (média × chamadas), não pela consulta mais lenta: uma de 5 ms chamada um milhão de vezes pesa mais que uma de 2 s chamada uma vez por dia.

Capítulo 5Transações e ACID

Pergunta-gatilho

Um pagamento é registrado e, na linha seguinte, a atualização da comanda falha. O que fica gravado no banco?

Ao final, você consegue
  • Explicar as quatro garantias ACID.
  • Usar transações no Prisma, no SQLAlchemy e no GORM.
  • Evitar os erros que deixam transações longas ou abertas.

5.1 ACID

LetraGarantia
AtomicidadeTudo ou nada. Se algo falha no meio, nada fica gravado. (A resposta da pergunta-gatilho, se as duas operações estiverem na mesma transação.)
ConsistênciaA transação leva o banco de um estado válido a outro: as restrições valem no fim.
IsolamentoTransações simultâneas não se atrapalham... até certo ponto, que é o capítulo 6.
DurabilidadeDepois do COMMIT, sobrevive a queda de energia (graças ao WAL).

5.2 Nas suas ferramentas

Prisma (RH): transação interativaawait prisma.$transaction(async (tx) => {
  const pag = await tx.pagamento.create({ data: { comandaId, valor } });
  await tx.comanda.update({ where: { id: comandaId }, data: { status: 'paga' } });
  return pag;
}, { timeout: 5000 });          // se qualquer linha lançar erro, ROLLBACK de tudo
SQLAlchemy 2 (Julielton)with Session(engine) as s, s.begin():     # COMMIT ao sair; ROLLBACK se houver exceção
    s.add(Pagamento(comanda_id=cid, valor=v))
    s.get(Comanda, cid).status = "paga"
GORM (MesaPay)err := db.Transaction(func(tx *gorm.DB) error {
    if err := tx.Create(&pagamento).Error; err != nil { return err }       // erro → ROLLBACK
    return tx.Model(&Comanda{}).Where("id = ?", id).Update("status", "paga").Error
})
Três erros clássicos
  • Usar o cliente global dentro da transação: no Prisma, chamar prisma.x em vez de tx.x dentro do $transaction executa fora da transação. No GORM, o mesmo com db em vez de tx.
  • Chamada externa dentro da transação (Evolution, e-mail, Anthropic): a transação fica aberta segurando locks enquanto a rede demora. E se a chamada externa der certo e o COMMIT falhar, a mensagem foi enviada para algo que não existe. Faça o externo depois do commit, de preferência via fila (padrão outbox, Módulo 5).
  • Transação esquecida aberta (idle in transaction): segura locks e impede o vacuum. Configure idle_in_transaction_session_timeout (capítulo 9).

Capítulo 6Isolamento e anomalias

Pergunta-gatilho

Duas transações leem o saldo (R$ 100), cada uma subtrai R$ 30 e grava. Qual o saldo final? Qual deveria ser?

Ao final, você consegue
  • Nomear e reproduzir as anomalias de concorrência.
  • Prever o que cada nível de isolamento do Postgres impede.
  • Tratar erros de serialização com retry.

6.1 As anomalias

AnomaliaO que acontece
Leitura sujaLer dado não confirmado de outra transação. O Postgres nunca permite.
Leitura não repetívelLer a mesma linha duas vezes na transação e obter valores diferentes
FantasmaRepetir uma consulta com WHERE e aparecerem linhas novas
Atualização perdida (lost update)Duas transações leem, calculam e gravam: a segunda sobrescreve a primeira (a pergunta-gatilho: o saldo final fica 70 em vez de 40)
Write skewDuas transações leem o mesmo conjunto, decidem com base nele e gravam linhas diferentes, quebrando uma regra (ex.: "pelo menos um gerente de plantão", e os dois saem ao mesmo tempo)

6.2 Os níveis no Postgres

NívelComo funcionaLost update / write skew
Read Committed (padrão)Cada comando vê o que estava confirmado quando ele começouLost update acontece no padrão "ler → calcular na aplicação → gravar"
Repeatable ReadA transação inteira vê um retrato (snapshot) do inícioLost update vira erro 40001 (precisa de retry). Write skew ainda passa
SerializableGarante resultado equivalente a alguma execução em série (SSI)Ambos viram erro 40001. Exige retry sempre

6.3 Reproduza com dois terminais

-- preparação:  CREATE TABLE conta (id int PRIMARY KEY, saldo numeric); INSERT INTO conta VALUES (1, 100);
-- Terminal A                              -- Terminal B
BEGIN;                                     BEGIN;
SELECT saldo FROM conta WHERE id=1; -- 100
                                           SELECT saldo FROM conta WHERE id=1; -- 100
UPDATE conta SET saldo = 70 WHERE id=1;    -- (a aplicação calculou 100 - 30)
COMMIT;
                                           UPDATE conta SET saldo = 70 WHERE id=1;  -- também calculou 100 - 30
                                           COMMIT;
SELECT saldo FROM conta;  -- 70   ← os R$ 30 da transação A sumiram

Agora repita com BEGIN ISOLATION LEVEL REPEATABLE READ; nos dois terminais: o UPDATE do B falha com could not serialize access due to concurrent update. Por fim, repita no Read Committed, mas escrevendo SET saldo = saldo - 30: o resultado fica correto (40), porque o cálculo foi para dentro do banco (capítulo 7).

Retry de erro de serialização (TypeScript, genérico)async function comRetry<T>(fn: () => Promise<T>, tentativas = 3): Promise<T> {
  for (let i = 1; ; i++) {
    try { return await fn(); }
    catch (e: any) {
      const serializacao = e?.code === '40001' || e?.code === '40P01';   // serialização / deadlock
      if (!serializacao || i >= tentativas) throw e;
      await new Promise((r) => setTimeout(r, 20 * i + Math.random() * 30));  // backoff com jitter
    }
  }
}

7.3 Fila no Postgres com SKIP LOCKED

Vários workers pegando tarefas sem pegar a mesmaWITH proxima AS (
  SELECT id FROM tarefa
  WHERE status = 'pendente' AND executar_em <= now()
  ORDER BY executar_em
  FOR UPDATE SKIP LOCKED          -- pula as linhas que outro worker já travou
  LIMIT 10
)
UPDATE tarefa SET status = 'processando', inicio = now()
FROM proxima WHERE tarefa.id = proxima.id
RETURNING tarefa.*;

Para volumes pequenos e médios, isso dispensa o Redis. O Julielton já faz exatamente isso em src/mabsol_docs/tarefas.py: o web só grava a tarefa, e o worker reserva com FOR UPDATE SKIP LOCKED, com tentativas máximas e devolução das tarefas travadas há mais de 30 minutos. Leia o arquivo com este capítulo ao lado. O marketZapp usa BullMQ (Redis), que também é uma boa escolha. O Módulo 5 compara os dois.

7.4 Deadlocks

A transação A trava a linha 1 e quer a 2. A B trava a 2 e quer a 1. O Postgres detecta, mata uma delas (erro 40P01) e a outra segue. Prevenção: sempre travar na mesma ordem (por exemplo, ordenar os IDs antes de atualizar vários registros), manter as transações curtas, e fazer retry do erro.

8.1 O que uma ferramenta de migração precisa fazer

  1. Guardar no próprio banco quais migrações já rodaram (tabela de controle).
  2. Aplicar as pendentes em ordem, cada uma numa transação quando possível.
  3. Ser versionada no Git junto com o código que depende dela.

8.2 Expand/contract (mudança em várias etapas)

Durante um deploy, a versão nova e a antiga do app rodam ao mesmo tempo por alguns segundos, e no rollback a antiga volta a rodar. Toda migração precisa ser compatível com a versão anterior do código. A resposta à pergunta-gatilho é 3 a 4 deploys:

  1. Expand: adicionar nome_completo (nulo). O app novo grava nas duas colunas e lê da antiga.
  2. Backfill: copiar os dados em lotes (UPDATE ... WHERE id BETWEEN x AND y), sem uma transação gigante.
  3. Migrar a leitura: o app passa a ler de nome_completo e ainda grava nas duas.
  4. Contract: o app para de usar nome. No deploy seguinte, DROP COLUMN nome.

Parece muito trabalho, e é. Para sistemas pequenos com janela de manutenção aceitável, um único deploy com 30 segundos fora do ar pode ser uma decisão consciente. O importante é saber que existe a alternativa e o risco de cada caminho.

8.3 Operações que travam e as alternativas

OperaçãoProblemaAlternativa
CREATE INDEXBloqueia escritas na tabela durante a criaçãoCREATE INDEX CONCURRENTLY (fora de transação: no Prisma/Alembic, uma migração separada)

A fila de locks

Mesmo uma operação rápida precisa de um lock exclusivo por um instante. Se houver uma consulta longa rodando, o ALTER espera, e todas as consultas novas ficam na fila atrás dele: o sistema trava sem que a migração tenha feito nada ainda. Proteção: SET lock_timeout = '5s'; no início da migração. Se não conseguir o lock, ela falha e você tenta de novo, em vez de travar a produção.

Capítulo 9Pool, timeouts e vacuum

Ao final, você consegue
  • Dimensionar o pool de conexões.
  • Configurar timeouts que protegem o banco.
  • Explicar o que o vacuum faz e por que ele importa.

9.1 Pool de conexões

Cada conexão no Postgres é um processo, com alguns MB de memória. O max_connections padrão é 100. Some os pools de todas as instâncias e processos que falam com o banco (API, workers, scripts) e mantenha o total bem abaixo desse limite. Mais conexões não é mais rápido: além do número de núcleos, elas competem entre si.

FerramentaOnde configurar
pg (marketZapp)new Pool({ max: 10, idleTimeoutMillis: 30000, connectionTimeoutMillis: 5000 })
Prisma (RH)?connection_limit=10&pool_timeout=10 na DATABASE_URL (ou as opções do driver adapter, nas versões novas)
SQLAlchemy (Julielton)create_engine(url, pool_size=5, max_overflow=5, pool_pre_ping=True)
GORM (MesaPay)sqlDB.SetMaxOpenConns(10); sqlDB.SetMaxIdleConns(5); sqlDB.SetConnMaxLifetime(time.Hour)

Quando houver muitas instâncias, um PgBouncer na frente do Postgres multiplexa conexões. Para os seus volumes, um pool bem configurado basta.

9.2 Timeouts que protegem

Por usuário da aplicação (vale para todas as conexões dele)ALTER ROLE app SET statement_timeout = '15s';                   -- consulta descontrolada não roda para sempre
ALTER ROLE app SET idle_in_transaction_session_timeout = '60s'; -- transação esquecida aberta é encerrada
ALTER ROLE app SET lock_timeout = '10s';

9.3 MVCC e vacuum em um parágrafo

O Postgres não sobrescreve linhas: um UPDATE cria uma nova versão e marca a antiga como morta. É isso que permite que leitores não bloqueiem escritores (MVCC). As versões mortas são limpas pelo vacuum, que o autovacuum roda sozinho. Ele falha quando uma transação fica aberta por horas (a limpeza não pode remover versões que ela ainda pode ver), e a tabela incha. Monitore com pg_stat_user_tables (n_dead_tup, last_autovacuum) e não deixe transações abertas: o timeout de 9.2 já ajuda.

Apêndice AGabarito e revisão intercalada

Pré-teste

  1. Ponto flutuante não representa decimais exatamente: aparecem centavos errados. Use numeric ou centavos inteiros. (1.1)
  2. Não de forma eficiente: falta o prefixo à esquerda. (3.2)
  3. 1 consulta para a lista + N para os relacionados. Aparece em loops com acesso preguiçoso às relações. (2.2)
  4. Read Committed. Não impede o lost update no padrão ler-calcular-gravar. (6.2)
  5. É sobrescrita sem aviso. Soluções: lock otimista (409) ou lock pessimista. (7.1)
  6. Estatísticas desatualizadas ou distribuição irregular, o que leva a um plano ruim: rode ANALYZE. (4.1)
  7. Bloqueia as escritas na tabela durante a criação. Use CONCURRENTLY. (8.3)
  8. Mudar o schema em etapas compatíveis: adicionar, migrar dados e leitura, e só depois remover. (8.2)
  9. Vários workers pegam tarefas diferentes, sem esperar nem duplicar. (7.3)
  10. Segura locks e conexão durante a latência da rede, e cria inconsistência se o commit falhar. (5.2)
  11. A restrição UNIQUE no banco. A validação na aplicação tem janela de corrida. (1.2)
  12. Conexões recusadas (too many clients) e erros intermitentes sob carga. (9.1)

Capítulos 1 e 2

  1. Guarda o instante absoluto. Sem fuso, o mesmo valor significa horas diferentes conforme o servidor.
  2. As duas requisições consultam "não existe" antes de qualquer uma inserir, e as duas inserem.
  3. Sem ele, mesas excluídas (soft delete) continuariam ocupando o número.
  4. Preço unitário copiado para o item do pedido no momento da venda.
  5. GROUP BY colapsa as linhas em grupos. A janela calcula sobre o grupo e mantém as linhas.
  6. Se o evento já existia, nada é inserido e nada volta: sabe-se que é duplicata.
  7. Log de consultas ligado e contagem de consultas por requisição.

Capítulos 3 e 4

  1. A lista ordenada por sobrenome não acha "todas as Marias" sem o sobrenome.
  2. (status, inicio): igualdade, depois intervalo.
  3. O índice guarda email, não lower(email): crie um índice de expressão.
  4. GIN com gin_trgm_ops.
  5. De dentro para fora: o nó mais indentado executa primeiro.
  6. Muita leitura descartada: falta um índice adequado.
  7. Com poucas linhas, ler a tabela inteira é mais barato.
  8. O impacto real é média × chamadas.

Capítulos 5 a 7

  1. Ex.: pagamento + fechar comanda juntos (A), valor não negativo (C), dois caixas simultâneos (I), sobrevive à queda (D).
  2. Executa fora da transação: não reverte junto.
  3. Lock segurado durante a rede, e mensagem enviada para algo que pode não ser confirmado.
  4. Lost update.
  5. Duas pessoas reservam as duas últimas mesas de uma área com limite de lotação, cada uma lendo "1 vaga".
  6. Repetir a transação inteira (com backoff).
  7. Estoque: atômica. Reserva única: UNIQUE. Formulário: otimista. Fila: SKIP LOCKED.
  8. Seguraria o lock durante minutos e bloquearia os outros usuários.
  9. As linhas travadas por um worker são puladas pelos outros.
  10. Travar sempre na mesma ordem, transações curtas, retry.

Capítulos 8 e 9

  1. Tabela de controle, ordem, versionamento no Git. No marketZapp falta a tabela de controle.
  2. Durante o deploy e no rollback a versão antiga roda com o schema novo.
  3. Adicionar coluna e gravar nas duas → backfill → ler da nova → parar de usar a antiga → drop.
  4. Falhar rápido em vez de enfileirar todo o tráfego atrás do ALTER.
  5. Além dos núcleos, as conexões competem por CPU e locks.
  6. statement_timeout, idle_in_transaction_session_timeout, lock_timeout.
  7. O vacuum não pode remover versões que a transação antiga ainda pode enxergar.

Revisão intercalada

Qual o problema e a correção?
  1. const n = await count(); await insert({ numero: n + 1 }) para gerar o número do pedido.
  2. Migração do Alembic: op.create_index('ix_x', 'grande', ['col']) rodando em horário de pico.
  3. Listagem de candidatos lenta. O log mostra 201 consultas por requisição.
  4. Relatório soma valor (double precision) e dá R$ 1.234,5699999.
  5. Webhook processa o mesmo evento duas vezes quando a Evolution reenvia.
  6. O Postgres fica lento toda tarde, e pg_stat_activity mostra uma conexão idle in transaction desde a manhã.
  1. Corrida: duas requisições pegam o mesmo n (cap. 6 e 7). Use sequence/identity, ou UNIQUE + retry.
  2. Bloqueia escritas (cap. 8.3). Use postgresql_concurrently=True numa migração fora de transação, em horário de pouco uso.
  3. N+1 (cap. 2.2). Use include/selectinload/Preload ou um join.
  4. Tipo de ponto flutuante para dinheiro (cap. 1.1). Migre para numeric(12,2).
  5. Falta idempotência (cap. 2.1). INSERT ... ON CONFLICT DO NOTHING com o ID do evento.
  6. Transação esquecida aberta (cap. 5.2 e 9). Corrija o código e configure idle_in_transaction_session_timeout.
