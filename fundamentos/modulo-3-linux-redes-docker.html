Capítulo 1Linux de servidor

Pergunta-gatilho

Você entra por SSH na VPS. Liste, de cabeça, cinco comandos que daria para entender o estado da máquina.

Ao final, você consegue
  • Navegar pela hierarquia de diretórios de um servidor e saber onde cada coisa fica.
  • Ler e ajustar permissões e donos de arquivos.
  • Inspecionar processos, memória e disco, e encerrar processos do jeito certo.

1.2 Usuários e permissões

Cada arquivo tem um dono, um grupo e permissões de leitura (r=4), escrita (w=2) e execução (x=1) para dono, grupo e outros.

$ ls -l /opt/infra/backup/backup.sh
-rwxr-x--- 1 root deploy 9120 nov 10 03:00 backup.sh
 │└┬┘└┬┘└┬┘
 │ │  │  └── outros: nada (0)
 │ │  └───── grupo deploy: ler e executar (5)
 │ └──────── dono root: ler, escrever, executar (7)   → chmod 750
 └────────── "-" arquivo comum, "d" diretório, "l" link
  • chmod 600 .env: só o dono lê e escreve. É o certo para arquivos com segredo.
  • chown deploy:deploy arquivo: muda dono e grupo.
  • Em diretório, o x significa "pode entrar". Sem ele, nem listando você acessa os arquivos de dentro.
  • Menor privilégio: a aplicação roda com um usuário sem poderes, e só você usa sudo. O deploy.md do marketZapp já cria um "usuário sem root para a aplicação".
Erro comum: estar no grupo docker

Colocar um usuário no grupo docker é dar root a ele: quem fala com o daemon do Docker consegue montar / do host num container e fazer qualquer coisa. Trate o grupo docker como trata o sudo.

1.3 Processos e sinais

ps aux --sort=-%mem | head      # quem mais usa memória
htop                            # visão interativa (F6 ordena, F9 envia sinal)
pgrep -af node                  # processos cujo comando contém "node"
kill -TERM 1234                 # pede para encerrar (o programa pode limpar e sair)
kill -KILL 1234                 # mata na hora; sem limpeza (último recurso)

SIGTERM (15) é um pedido educado: o app pode fechar conexões, terminar o job atual da fila e sair. SIGKILL (9) não pode ser capturado nem ignorado. O docker stop manda SIGTERM, espera 10 segundos e depois manda SIGKILL. Por isso o app precisa tratar o SIGTERM (app.close() no Fastify, worker.close() no BullMQ) para não perder jobs no meio.

Código de saída: 0 é sucesso, qualquer outro valor é erro. O 137 (128+9) indica que o processo foi morto por SIGKILL, normalmente pelo OOM killer por falta de memória.

1.4 Memória e disco

free -h                         # "available" é o que importa, não "free"
df -h                           # espaço por partição
df -i                           # inodes: dá para "encher" com milhões de arquivos pequenos
du -sh /var/lib/docker/* | sort -h   # quem ocupa espaço
sudo dmesg -T | grep -i -E "killed process|out of memory"   # houve OOM?

O Linux usa a memória livre como cache de disco, então "free" baixo é normal. Preocupe-se quando o available for baixo e o swap estiver sendo usado o tempo todo.

2.2 Scripts que falham de forma segura

O backup.sh do RH começa com set -euo pipefail. É o cabeçalho que todo script de operação deveria ter:

  • -e: para no primeiro comando que falhar, em vez de seguir e fazer estrago.
  • -u: erro ao usar uma variável não definida. Sem isso, rm -rf "$PASTA/" com PASTA vazia vira rm -rf /.
  • -o pipefail: um pipe falha se qualquer parte falhar. Sem isso, pg_dump | gzip "dá certo" mesmo se o pg_dump falhar, porque o gzip terminou bem. Imagine isso num backup.

Sempre coloque variáveis entre aspas ("$ARQ") e valide os scripts com shellcheck (apt install shellcheck), que acha esses problemas automaticamente.

2.3 SSH produtivo

~/.ssh/config no seu notebookHost vps
    HostName 203.0.113.50        # IP da VPS
    User deploy
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 30

# agora: ssh vps · scp arquivo vps:/tmp/ · rsync -avz pasta/ vps:/opt/app/
# túnel para acessar o Postgres da VPS (publicado só no loopback) do seu notebook:
ssh -L 5433:127.0.0.1:5432 vps     # e conecte em localhost:5433

O túnel SSH é o jeito certo de acessar serviços que você (corretamente) não expôs na internet, como o Postgres do marketZapp em 127.0.0.1:5432. Use tmux na VPS para que comandos longos (uma restauração, por exemplo) não morram se a conexão cair.

Capítulo 3systemd: serviços e timers

Pergunta-gatilho

A VPS ficou desligada das 3h às 5h para manutenção. O backup das 3h30 rodou? Como você descobre?

Ao final, você consegue
  • Ler e escrever units de serviço e de timer.
  • Operar serviços com systemctl e investigar com journalctl.
  • Justificar o uso de timers em vez de cron.

3.1 O exemplo resolvido: o timer do backup do RH

[Timer]
OnCalendar=*-*-* 03:30:00     # todo dia às 03:30
RandomizedDelaySec=20m        # sorteia um atraso de até 20 min (evita todo mundo no minuto cheio)
Persistent=true               # se a máquina estava desligada, roda assim que ligar
[Install]
WantedBy=timers.target

A resposta à pergunta-gatilho é o Persistent=true: o systemd guarda quando o timer rodou pela última vez e, ao ligar, executa o que ficou para trás. O cron simplesmente pula. Essa é uma das vantagens dos timers, junto com: logs automáticos no journal, dependências (rodar só depois que a rede subir), limites de recursos e systemctl list-timers para ver a próxima execução.

O timer dispara um serviço de mesmo nome (francal-backup.service), normalmente do tipo Type=oneshot (roda e termina).

3.2 Os comandos do dia a dia

systemctl status francal-backup.service      # estado, últimas linhas de log, PID
systemctl list-timers --all                  # próximos e últimos disparos
sudo systemctl start francal-backup.service  # roda agora, à mão
sudo systemctl enable --now algo.timer       # habilita no boot e já inicia
sudo systemctl daemon-reload                 # OBRIGATÓRIO depois de editar uma unit
journalctl -u francal-backup.service --since today
journalctl -u francal-backup.service -n 50 --no-pager
journalctl -p err -b                         # só erros desde o último boot

3.3 Um serviço que se recupera sozinho

/etc/systemd/system/exemplo.service[Unit]
Description=Exemplo de API
After=network-online.target
Wants=network-online.target

[Service]
User=deploy
WorkingDirectory=/opt/app
EnvironmentFile=/opt/app/.env
ExecStart=/usr/bin/node dist/server.js
Restart=on-failure          # reinicia se cair com erro
RestartSec=5
# endurecimento barato:
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/opt/app/uploads

[Install]
WantedBy=multi-user.target

Nos seus projetos, os apps rodam em Docker com restart: always, e o systemd cuida do Docker e dos timers. O exemplo acima serve para entender o que o restart do Docker faz por você, e para scripts que não precisam de container.

Capítulo 4IP, portas e DNS

Pergunta-gatilho

  • Descobrir o que está escutando em cada porta.
  • Consultar e interpretar registros DNS.
  • Desenhar o caminho completo de uma requisição na sua infra.

4.1 O caso do celular que não abria o localhost

Um programa que escuta numa porta escolhe também em qual endereço escutar (o bind):

BindQuem consegue conectar
127.0.0.1 (loopback)Só processos da própria máquina
192.168.0.10Quem alcança esse endereço (a rede local)
0.0.0.0Todas as interfaces: loopback, rede local e internet, se houver IP público

Vite e Next escutam em 127.0.0.1 por padrão, por segurança. Por isso o celular, que é outra máquina, não conseguia conectar. A correção é vite --host ou next dev -H 0.0.0.0, e às vezes liberar a porta no firewall do notebook. O mesmo princípio explica o HOST: 0.0.0.0 no compose do marketZapp: dentro do container, o app precisa escutar em todas as interfaces, porque o tráfego chega pela interface de rede do container, e não pelo loopback dele.

Erro comum: localhost dentro do container

Dentro de um container, localhost é o próprio container, e não a VPS nem o outro container. O backend fala com o Postgres pelo nome do serviço na rede do Docker (anunciai-db:5432), não por localhost:5432.

4.2 Quem está escutando?

sudo ss -tlnp            # t=TCP l=escutando n=sem resolver nomes p=processo
State   Local Address:Port   Process
LISTEN  127.0.0.1:5432       docker-proxy   ← Postgres só no loopback  ✔
LISTEN  0.0.0.0:443          docker-proxy   ← Caddy aberto para fora   ✔ (é o objetivo)
LISTEN  0.0.0.0:6379         redis-server   ← Redis aberto para a internet ✘ PERIGO

nc -zv 203.0.113.50 5432    # de FORA da VPS: a porta responde?
curl -v telnet://host:porta # alternativa quando não há nc

Rodar ss -tlnp é o primeiro passo de qualquer auditoria. Qualquer coisa em 0.0.0.0 que não seja 22, 80 ou 443 merece uma justificativa.

Capítulo 5TLS, proxy reverso e firewall

Pergunta-gatilho

O deploy.md do marketZapp diz que o TRUST_PROXY errado "quebra dois anti-spam em silêncio". Por que uma configuração de proxy afetaria um anti-spam?

Ao final, você consegue
  • Explicar como o TLS e os certificados funcionam, e o papel do Let's Encrypt.
  • Configurar um proxy reverso e os cabeçalhos X-Forwarded-*.
  • Explicar por que o ufw não protege portas do Docker e o que faz o script do RH.

5.1 TLS em três ideias

  1. Cifra o tráfego, para que ninguém no caminho leia.
  2. Autentica o servidor: o certificado prova que quem responde é dono do domínio, assinado por uma autoridade (CA) em que o navegador confia.
  3. Garante integridade: ninguém altera os dados no caminho.

O Let's Encrypt emite certificados gratuitos de 90 dias pelo protocolo ACME. O Caddy faz isso sozinho: pede, valida o domínio (desafio HTTP-01 na porta 80 ou TLS-ALPN na 443) e renova. Por isso o comentário do firewall do RH diz que o Caddy precisa conseguir sair para a internet.

Com Cloudflare no meio existem dois TLS: navegador ↔ Cloudflare e Cloudflare ↔ VPS. Use o modo Full (strict), que exige um certificado válido na VPS. O modo "Flexible" deixa o segundo trecho em HTTP puro, e o modo "Full" sem strict aceita qualquer certificado.

curl -vI https://api.marketzapp.com.br 2>&1 | grep -E "subject|issuer|expire"
openssl s_client -connect host:443 -servername host </dev/null | openssl x509 -noout -dates

5.2 Proxy reverso e o X-Forwarded-For

O Caddy recebe a conexão e a repassa ao container. Para o app, quem conectou foi o Caddy, então o IP de origem é o do Caddy. O IP real do usuário chega num cabeçalho, X-Forwarded-For (ou CF-Connecting-IP, posto pela Cloudflare). Isso cria dois problemas opostos:

  • Sem confiar no proxy (trustProxy desligado): o app vê todo mundo com o mesmo IP, o do Caddy. O rate limit por IP bloqueia todos de uma vez, ou não bloqueia ninguém. É o "anti-spam quebrado em silêncio" do marketZapp.
  • Confiando em qualquer um: um atacante que fala direto com o app manda X-Forwarded-For: 1.2.3.4 e escolhe o próprio IP, burlando o rate limit.

Configure para confiar exatamente no número de saltos ou nas faixas de proxy que existem (Caddy, e Cloudflare se houver), e garanta que ninguém fale com o app sem passar por eles, que é o que o firewall faz.

5.3 Firewall e Docker: o caso do RH

Quando você publica -p 5432:5432, o Docker cria uma regra de NAT que redireciona o pacote para o IP do container. Esse pacote segue pela cadeia FORWARD, e não pela INPUT, que é onde o ufw trabalha. Daí as duas defesas da sua infra:

  1. Não publicar o que não precisa ser público, ou publicar só no loopback (127.0.0.1:5432:5432, como no marketZapp). É a defesa principal.
  2. Regras na cadeia DOCKER-USER, que o Docker consulta antes das próprias regras e nunca sobrescreve. O cloudflare-only.sh do RH usa essa cadeia para aceitar 80/443 só das faixas da Cloudflare, com -i eth0 para não bloquear o tráfego de saída dos containers.

Pergunta-gatilho

Ao final, você consegue

  • Escolher entre volume nomeado, bind mount e volume anônimo.
  • Configurar redes, healthchecks, limites e rotação de logs no compose.

6.1 Imagem, camadas e cache

Uma imagem é uma pilha de camadas somente leitura, uma por instrução do Dockerfile. Um container é uma imagem com uma camada gravável por cima, que some quando o container é removido. O build reaproveita camadas cujo conteúdo não mudou: por isso a ordem das instruções importa.

Errado · qualquer mudança no código reinstala tudo, e roda como rootFROM node:22
COPY . .
RUN npm install
CMD ["npm", "start"]
Certo · multi-stage, cache de dependências, usuário sem privilégio# --- build ---
FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci                                  # só refaz se o lockfile mudar
COPY tsconfig.json ./
COPY src ./src
RUN npm run build && npm prune --omit=dev

# --- runtime ---
FROM node:22-alpine
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY package.json ./
USER node                                   # a imagem oficial já tem esse usuário
EXPOSE 3001
CMD ["node", "dist/server.js"]              # node direto: recebe o SIGTERM (npm start não repassa bem)
  • .dockerignore com node_modules, .env*, .git: build mais rápido e sem segredo dentro da imagem.
  • Fixe a versão da imagem base (node:22-alpine, não node:latest). Para reprodutibilidade total, use o digest (@sha256:...).
  • docker history imagem mostra as camadas e o tamanho de cada uma.

Comandos perigosos

docker compose down -v apaga os volumes do projeto. docker volume prune -a apaga todos os volumes não usados por algum container, inclusive os nomeados: o banco de um serviço que estava removido some junto. (Nas versões recentes do Docker, o prune sem -a remove só os anônimos. Confira com docker volume prune --help.) Leia duas vezes antes de rodar em produção.

6.3 Redes

Cada projeto do compose ganha uma rede própria, e os serviços se encontram pelo nome (DNS interno do Docker). Projetos diferentes ficam isolados, a não ser que compartilhem uma rede declarada como external. É o que faz a rede edge da sua VPS: o Caddy está nela, e cada app que precisa ser publicado é conectado a ela. O Postgres de cada app fica só na rede interna do próprio projeto, invisível ao Caddy e aos outros apps.

6.4 O compose de produção, item por item

Trecho comentadoservices:
  api:
    image: ghcr.io/usuario/app:${TAG:?defina TAG}   # tag do commit, não latest
    restart: unless-stopped
    env_file: .env                                  # chmod 600
    depends_on:
      db: { condition: service_healthy }            # espera o banco ficar PRONTO, não só "iniciado"
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:3001/health"]
      interval: 30s
      timeout: 5s
      retries: 3
    deploy:
      resources: { limits: { memory: 512M } }       # um vazamento não derruba a VPS inteira
    logging:
      driver: json-file
      options: { max-size: "10m", max-file: "5" }   # sem isso, o log cresce até encher o disco
    networks: [interna, edge]
  db:
    image: postgres:16-alpine
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck: { test: ["CMD-SHELL", "pg_isready -U app"], interval: 5s, retries: 10 }
    networks: [interna]                             # nenhuma porta publicada
volumes: { pgdata: {} }
networks: { interna: {}, edge: { external: true } }
Caso real · o !override do marketZapp

Ao combinar docker-compose.yml e docker-compose.prod.yml, o Compose concatena listas como ports. Sem o !override, o Postgres ficaria com 5432:5432 (do arquivo base) e 127.0.0.1:5432:5432: abriria para a internet e depois quebraria com "address already in use". Use docker compose -f a.yml -f b.yml config para ver o resultado final da mescla antes de subir.

O "conflito de Postgres no docker-compose" que você já teve costuma vir daí: dois serviços, ou um Postgres instalado no host e outro no container, querendo a mesma porta 5432 do host. Diagnóstico: sudo ss -tlnp | grep 5432. Correção: publicar em outra porta (55432:5432, como no teste do Julielton) ou não publicar.

Capítulo 7Logs e monitoramento

Pergunta-gatilho

Se o backup do RH falhar todas as noites a partir de hoje, quando você vai ficar sabendo?

Ao final, você consegue
  • Escrever logs úteis para diagnóstico.
  • Montar monitoramento externo de disponibilidade e de tarefas agendadas.
  • Diferenciar logs, métricas e alertas.

7.1 Logs que ajudam

  • Estruturados (JSON): {"level":"error","msg":"falha ao enviar","jobId":"msg-123","ms":5021}. Dá para filtrar com jq e agregar. O pino do Fastify já faz isso. No Express, use pino-http. No Go, o log/slog da biblioteca padrão.
  • Um ID por requisição (reqId) em todas as linhas daquela requisição, para seguir o caminho dela.
  • Níveis: error = alguém precisa agir; warn = estranho, mas tratado; info = eventos de negócio; debug desligado em produção.
  • Contexto, não segredo (Módulo 1, 10.5): IDs, durações e status, nunca tokens, senhas ou CPF.

7.2 Três camadas de observação

CamadaPerguntaFerramenta mínima
LogsO que aconteceu, em detalhe?docker compose logs, journalctl, rotação configurada
MétricasComo está ao longo do tempo (CPU, disco, latência)?Painel do provedor da VPS. Depois: Netdata, ou Prometheus + Grafana
AlertasQuando preciso agir?Monitor externo de uptime + "dead man's switch"

7.3 Monitoramento externo: o mínimo que vale ouro

  1. Uptime: um serviço externo (UptimeRobot, Better Stack, ou o Uptime Kuma em outra máquina) chama https://.../health a cada minuto e avisa por e-mail ou Telegram se falhar. Tem que ser externo: um monitor dentro da VPS morre junto com ela.
  2. Dead man's switch para tarefas agendadas: o backup, ao terminar com sucesso, faz um curl para uma URL do healthchecks.io (ou similar). Se o ping não chegar no horário esperado, você recebe o alerta. Isso responde à pergunta-gatilho: sem ele, a resposta é "quando precisar restaurar e descobrir que não tem backup".
  3. Disco: alerta com 80% de uso. Disco cheio derruba o Postgres, e o Postgres derruba tudo.
Final de um script de backup com ping de sucesso e de falhatrap 'curl -fsS -m 10 --retry 3 "$HC_URL/fail" >/dev/null' ERR   # avisa a falha
# ... backup ...
curl -fsS -m 10 --retry 3 "$HC_URL" >/dev/null                   # avisa o sucesso

7.4 O endpoint /health

Separe dois conceitos: liveness ("o processo está vivo?", que só responde 200) e readiness ("consigo atender?", que testa o banco e o Redis com timeout curto). O healthcheck do Docker e o monitor externo usam o de readiness. Não exponha detalhes internos nele: {"ok":true} basta.

Verifique · Capítulo 7
  1. Por que o monitor de uptime precisa estar fora da VPS?
  2. O que é um dead man's switch e qual problema ele resolve?
  3. Diferencie liveness de readiness.

Capítulo 8Backup e restauração

Pergunta-gatilho

A VPS do RH foi perdida agora. Quantas horas de dados você perde, e quanto tempo leva para o site voltar? Escreva os números antes de ler.

Ao final, você consegue
  • Definir RPO e RTO para cada sistema.
  • Explicar as decisões do backup do RH (restic, stdin, banco + arquivos juntos).
  • Executar e cronometrar uma restauração completa.

8.1 Vocabulário

  • RPO (Recovery Point Objective): quanto dado você aceita perder. Backup diário = RPO de até 24 h.
  • RTO (Recovery Time Objective): em quanto tempo o sistema precisa voltar.
  • Regra 3-2-1: 3 cópias, em 2 mídias diferentes, 1 fora do local. Versão moderna: 3-2-1-1-0, com 1 cópia imutável ou offline e 0 erros na restauração testada.

8.2 Exemplo resolvido: as decisões do backup.sh do RH

DecisãoPor quê
Banco e currículos juntosOs arquivos têm nome sorteado. Quem é dono de cada PDF está só no banco. Restaurar um sem o outro devolve "uma pilha de PDFs anônimos".
resticCriptografa (currículo é dado pessoal e vai para o armazenamento de terceiros), deduplica (o PDF que não mudou é guardado uma vez) e expira sozinho (forget --prune).
Dump do banco por stdinO dump nunca existe em disco em texto claro, nem ocupa espaço.
Timer com Persistent=trueNão pula o dia se a VPS estava desligada (capítulo 3).
Timer separado de verificaçãorestic check confere a integridade do repositório periodicamente.

É um desenho bom. O que falta, e que nenhum script resolve sozinho: (1) confirmar que está rodando na VPS, (2) alerta quando falhar (capítulo 7) e (3) uma restauração testada e cronometrada, que é a missão M6.

pg_dump (lógico)pg_basebackup + WAL (físico)

Dump e restauração no formato custom# dump (de dentro do container, saída no host)

8.4 O que entra no backup (e o que se esquece)

  • Banco de dados
  • Uploads (currículos, PDFs gerados do Julielton)
  • Arquivos .env de produção, num cofre separado e criptografado
  • A senha do repositório restic, fora da VPS. Sem ela o backup é ilegível, inclusive para você
  • Configuração da infra (/opt/infra), que já está no Git do RH: ótimo
  • Volumes de serviços de terceiros com estado (sessão do WhatsApp na Evolution)

8.5 O roteiro de restauração

  1. Máquina limpa (VM de teste), cronômetro ligado.
  2. Instalar Docker e restic, e clonar o repositório da infra.
  3. backup.sh --listar e --restaurar latest /restauracao.
  4. Subir o Postgres, restaurar o dump, apontar os uploads.
  5. Subir a aplicação e conferir: login funciona, um currículo abre, a contagem de registros bate.
  6. Parar o cronômetro: esse é o seu RTO real. Anotar tudo que não estava documentado.

  1. Defina RPO e RTO e dê os valores atuais do RH.
  2. Por que banco e uploads precisam ir juntos no RH?
  3. Por que guardar a senha do restic fora da VPS?
  4. Quando faria sentido trocar pg_dump por backup físico com WAL?

Capítulo 9Diagnóstico: onde olhar

Pergunta-gatilho

Um cliente manda "o sistema não abre". Escreva os seus 5 primeiros passos, na ordem.

Ao final, você consegue
  • Seguir um método de diagnóstico em vez de tentar coisas ao acaso.
  • Mapear cada sintoma comum para a camada provável.
  • Escrever um runbook para os seus sistemas.

9.1 O método

  1. Reproduza e delimite: falha para todos ou para um? Em todas as páginas ou numa rota? Desde quando? O que mudou (deploy, renovação de certificado, disco)?
  2. Siga o caminho da requisição (figura 4.1), de fora para dentro, e ache a primeira caixa que falha.
  3. Hipótese → teste → conclusão, uma de cada vez. Anote o que testou: na terceira hora ninguém lembra.
  4. Mitigue antes de entender tudo: se o deploy de 10 minutos atrás é o suspeito, faça rollback primeiro e investigue depois.
  5. Depois: escreva o que aconteceu (sem culpados), e transforme a causa em teste, alerta ou item de checklist.

9.3 Runbook

Um runbook é o roteiro escrito para "quando X acontecer, faça Y". Ele é escrito com calma para ser seguido sob pressão. Estrutura sugerida para cada sistema: (1) como entrar (host, usuário, onde está o compose), (2) verificação rápida (os 5 comandos), (3) problemas conhecidos com a solução, (4) como fazer rollback, (5) como restaurar o backup e (6) quem avisar. É a missão M2.

Capítulo 10Segurança da VPS

Ao final, você consegue
  • Auditar a sua VPS com um checklist e corrigir o que faltar.

Acesso

  • SSH só por chave: PasswordAuthentication no
  • PermitRootLogin no (ou prohibit-password)
  • Usuário próprio com sudo. A aplicação com usuário sem privilégio
  • fail2ban ou equivalente no SSH
  • Chaves antigas removidas de authorized_keys

Superfície exposta

  • ss -tlnp: só 22, 80 e 443 em 0.0.0.0
  • Bancos e Redis sem porta publicada, ou só em loopback
  • Firewall na DOCKER-USER quando houver proxy (Cloudflare)
  • Painéis administrativos (Evolution, pgAdmin) atrás de túnel SSH, não públicos

Atualizações

  • unattended-upgrades para patches de segurança
  • Imagens Docker atualizadas (Dependabot no compose ou revisão mensal)
  • Reboot periódico para aplicar o kernel novo

Dados e recuperação

  • .env com chmod 600
  • Backup criptografado fora da VPS, com alerta de falha
  • Restauração testada nos últimos 6 meses
  • Rotação de logs configurada
  • Monitor externo de uptime
  • Snapshot do provedor antes de mudanças grandes

Apêndice AGabarito e revisão intercalada

Pré-teste

  1. O servidor de desenvolvimento escuta em 127.0.0.1, que só aceita conexões da própria máquina. Use --host / 0.0.0.0. (4.1)
  2. sudo ss -tlnp. (4.2)
  3. O Docker faz NAT e o pacote passa pela cadeia FORWARD, não pela INPUT do ufw. (5.3)
  4. Nomeado: gerenciado pelo Docker, em /var/lib/docker/volumes. Bind: uma pasta do host que você escolhe. (6.2)
  5. Entre o proxy e o app: container parado, nome ou porta errados, rede. (9.2)
  6. RPO: quanto dado se aceita perder. RTO: em quanto tempo o sistema volta. (8.1)
  7. journalctl -u nome --since "1 hour ago". (3.2)
  8. CNAME: apelido de um nome para outro. TTL: tempo de cache da resposta. (4.3)
  9. Para o próprio container. (4.1)
  10. Logs de container sem rotação, imagens e cache de build antigos, volumes órfãos. (6.4, 6.5)
  11. SIGTERM pede o encerramento (dá para limpar). SIGKILL mata na hora, sem limpeza. (1.3)
  12. Só a restauração prova que o backup está completo, legível e que você sabe usá-lo. (8.5)

Capítulo 1

  1. 600 para o .env. 700 (ou 750 com grupo) para o script.
  2. Quem fala com o daemon monta o / do host num container como root.
  3. Foi morto por SIGKILL, provavelmente OOM. Confirme com dmesg -T | grep -i kill.
  4. O Linux usa a memória livre como cache. Olhe o "available".

Capítulo 2

  1. -e para no erro, -u barra variável vazia, pipefail faz o pipe falhar se o pg_dump falhar, mesmo que o gzip termine bem.
  2. Túnel: ssh -L 5433:127.0.0.1:5432 vps.
  3. Ex.: jq -c 'select(.status==500)' access.log | wc -l, adaptando o nome do campo ao formato do log do Caddy.

Capítulo 3

  1. Executa disparos perdidos enquanto a máquina estava desligada. O cron simplesmente pula.
  2. systemctl daemon-reload.
  3. journalctl -p err -b.

Capítulo 4

  1. O tráfego chega ao app pela interface de rede do container. Já a porta do host define quem de fora alcança, e o Postgres não deve ser alcançado de fora.
  2. Pelo nome do serviço, via DNS interno do Docker.
  3. Para que os caches expirem rápido depois da troca de IP.
  4. O IP da Cloudflare.

Capítulo 5

  1. Sigilo, autenticação do servidor, integridade.
  2. Flexible deixa o trecho Cloudflare → VPS sem cifra. Strict exige certificado válido.
  3. Desligado: todos com o IP do proxy. Confiar em tudo: o cliente forja o próprio IP.
  4. Ver 5.3: NAT/FORWARD. Defesas: publicar só no loopback (ou não publicar) e regras na DOCKER-USER.

Capítulo 6

  1. A camada do npm ci só é refeita quando o lockfile muda.
  2. Ver a tabela de 6.2.
  3. Que o banco passou no healthcheck, ou seja, está pronto para conexões.
  4. logging.options.max-size e max-file.
  5. docker compose -f a.yml -f b.yml config.

Capítulo 7

  1. Para não morrer junto com a VPS.
  2. Alerta quando um sinal esperado não chega. Detecta tarefas que pararam de rodar.
  3. Liveness: processo vivo. Readiness: consegue atender (dependências ok).

Capítulo 8

  1. RPO ≈ 24 h (backup diário). RTO desconhecido até a missão M6.
  2. O vínculo entre arquivo e candidato está só no banco.
  3. Sem ela o backup é ilegível. Se ela só existir na VPS perdida, perde-se tudo.
  4. Banco grande, ou RPO exigido de minutos.

Capítulo 9

  1. Reduz o tempo de impacto para o usuário. A investigação continua depois, com calma.
  2. 502: o proxy não alcança o app. 504: alcança, mas o app não responde a tempo.
  3. Variável/configuração faltando, dependência indisponível, OOM.

Revisão intercalada

Qual a causa provável e o primeiro comando?
  1. Depois de um docker compose down -v para "limpar", o sistema voltou sem nenhum dado.
  2. Os logs do rate limit mostram todos os acessos vindos de 172.18.0.2.
  3. O site funciona, mas a API dá 502 desde o último deploy.
  4. O backup "roda" todo dia, mas o arquivo do dump tem 20 bytes.
  5. O Postgres não sobe: "could not write to file: No space left on device".
  6. Você liberou ufw allow 3000, mas o celular continua sem acessar o app de desenvolvimento.
  7. O certificado expirou, embora o Caddy renove sozinho.
  1. -v apagou os volumes (6.2). Restaurar do backup (8.5). Nunca use -v em produção.
  2. trust proxy desligado: o IP é o do Caddy (5.2). Ajuste o número de saltos confiáveis.
  3. O container novo não subiu, ou mudou de nome/porta/rede (9.2): docker compose ps, logs do app e do Caddy.
  4. Pipe sem pipefail: o pg_dump falhou e o gzip "deu certo" (2.2). E faltou o alerta (7.3).
  5. Disco cheio (1.4, 9.2): df -h, docker system df, logs sem rotação (6.4).
  6. O app escuta em 127.0.0.1 (4.1). O firewall não muda isso: use --host.
  7. A renovação falhou: o desafio ACME foi bloqueado (firewall, Cloudflare) ou o Caddy não sai para a internet (5.1). Olhe os logs do Caddy.
