Capítulo 1Por que e o que testar

Pergunta-gatilho

Se você só pudesse escrever 5 testes no projeto do Julielton, quais seriam? Escreva os 5 títulos antes de continuar.

Ao final, você consegue
  • Explicar o valor de um teste em termos de custo do bug e de liberdade para mudar o código.
  • Priorizar o que testar com uma matriz de risco.
  • Transformar uma regra de negócio (RN) em casos de teste.

1.1 Para que servem os testes

A resposta comum é "achar bug". A resposta mais útil é: permitir mudar o código com segurança. Um projeto sem testes congela, porque toda mudança vira um risco que só aparece em produção. Com bons testes, você refatora, atualiza dependências e aceita código gerado por IA sabendo em segundos se algo quebrou. Testes também são documentação executável: o whatsapp.test.ts do marketZapp explica o contrato do webhook melhor que qualquer README, e nunca fica desatualizado, porque se ficar, quebra.

O custo de um bug cresce com a distância entre o momento em que ele nasce e o momento em que é descoberto: no editor, custa segundos; no CI, minutos; em produção, custa o tempo do cliente, a confiança e às vezes dados.

1.2 Os quatro pilares de um teste valioso (Khorikov)

PilarPergunta
Proteção contra regressãoSe alguém introduzir um bug aqui, o teste pega? Testes que executam mais código importante protegem mais.
Resistência a refatoraçãoSe eu reorganizar o código sem mudar o comportamento, o teste continua passando? Teste que quebra sem bug é falso positivo, e falsos positivos ensinam a equipe a ignorar os testes.
Feedback rápidoRoda em quanto tempo? Testes lentos deixam de ser rodados.
ManutenibilidadeÉ fácil de ler e de montar?

Os três primeiros competem entre si, e nenhum teste maximiza todos. Mas a resistência a refatoração não é negociável: um teste frágil tem valor negativo. É por isso que a regra é testar comportamento observável (o que a função devolve, o que a API responde, o que ficou gravado no banco) e não detalhes de implementação (qual método privado foi chamado, em que ordem).

1.3 O que testar primeiro: matriz de risco

Não tente cobrir tudo. Classifique cada funcionalidade por impacto se quebrar e probabilidade de quebrar (complexidade, frequência de mudança, histórico de bugs).

1.4 De regra de negócio para caso de teste

O REGRAS_DE_NEGOCIO.md do MesaPay, com códigos RN-XX, já é meio caminho andado. Para cada regra, escreva os casos com a técnica de partição e valor-limite: um caso típico de cada classe de entrada e os casos nas fronteiras.

Exemplo resolvido · uma RN fictícia no estilo do MesaPay

RN-XX: "A reserva pode ser cancelada sem multa até 2 horas antes do horário. Depois disso, cobra-se 20%. Reservas já iniciadas não podem ser canceladas."

  • Classes: mais de 2 h antes (sem multa), menos de 2 h (multa), já iniciada (erro).
  • Limites: exatamente 2 h antes ("até" inclui ou não? Pergunte ao cliente e registre na RN), 2 h menos 1 segundo, exatamente no horário.
  • Casos inválidos: reserva de outro estabelecimento, reserva já cancelada.

São 7 testes para uma regra de uma linha, e o caso de "exatamente 2 h" provavelmente revela uma ambiguidade que ninguém tinha decidido. Escrever o teste é uma forma de especificar.

Go · teste orientado por tabela (o padrão idiomático do MesaPay)func TestMultaCancelamento(t *testing.T) {
    inicio := time.Date(2026, 11, 20, 20, 0, 0, 0, time.UTC)
    casos := []struct {
        nome      string
        agora     time.Time
        multa     int // percentual
        erroEsper error
    }{
        {"3h antes, sem multa", inicio.Add(-3 * time.Hour), 0, nil},
        {"exatamente 2h antes, sem multa", inicio.Add(-2 * time.Hour), 0, nil},
        {"2h menos 1s, com multa", inicio.Add(-2*time.Hour + time.Second), 20, nil},
        {"já iniciada", inicio.Add(time.Minute), 0, ErrReservaIniciada},
    }
    for _, c := range casos {
        t.Run(c.nome, func(t *testing.T) {
            multa, err := MultaCancelamento(inicio, c.agora)
            if !errors.Is(err, c.erroEsper) { t.Fatalf("erro = %v, esperado %v", err, c.erroEsper) }
            if multa != c.multa { t.Errorf("multa = %d, esperado %d", multa, c.multa) }
        })
    }
}

Repare que o "agora" é parâmetro, não um time.Now() dentro da função. Isso torna a regra testável (capítulo 7).

Capítulo 2Anatomia de um bom teste

Pergunta-gatilho

Abra um teste seu de 3 meses atrás. Em 10 segundos, você consegue dizer qual regra ele protege?

Ao final, você consegue
  • Estruturar testes no padrão Arrange-Act-Assert.
  • Nomear testes como frases sobre o comportamento.
  • Reconhecer os cheiros de teste mais comuns.

2.1 Arrange, Act, Assert

Todo teste tem três partes: preparar o cenário, executar uma ação e verificar o resultado. Deixe as três visíveis, com uma linha em branco entre elas. A seção Act deve ter uma linha. Se precisa de várias chamadas para executar "uma ação", a API do código provavelmente está mal desenhada.

Errado · vários comportamentos e nome vagoit('vagas', async () => {
  const v = await criarVaga({ titulo: 'Dev' });
  expect(v.id).toBeDefined();
  await publicarVaga(v.id);
  expect((await buscar(v.id)).status).toBe('publicada');
  await arquivarVaga(v.id);
  expect((await buscar(v.id)).status).toBe('arquivada');
  await expect(publicarVaga(v.id)).rejects.toThrow();
});
Certo · um comportamento por teste, nome é uma frasedescribe('arquivamento de vaga', () => {
  it('não permite republicar uma vaga arquivada', async () => {
    const vaga = await fabrica.vaga({ status: 'arquivada' });   // Arrange

    const tentativa = publicarVaga(vaga.id);                     // Act

    await expect(tentativa).rejects.toThrow(VagaArquivadaError); // Assert
  });
});

Quando o teste da direita falhar, a mensagem já diz o que quebrou: "arquivamento de vaga › não permite republicar uma vaga arquivada". O da esquerda diz só "vagas".

2.2 Propriedades F.I.R.S.T.

  • Fast (rápido): unitários em milissegundos, a suíte inteira em poucos minutos.
  • Isolated (isolado): um teste não depende de outro nem da ordem de execução. O Vitest e o pytest podem rodar em paralelo ou em ordem aleatória.
  • Repeatable (repetível): o mesmo resultado na sua máquina, no CI e às 23h59 de 31 de dezembro.
  • Self-validating: passa ou falha sozinho, sem ninguém olhar um log.
  • Timely: escrito junto com o código, não "depois".

2.3 Fábricas e dados de teste

Montar objetos completos em cada teste deixa tudo verboso e frágil: quando um campo obrigatório novo aparece, 40 testes quebram. Use fábricas com valores padrão sensatos, e deixe o teste sobrescrever só o que importa para aquele caso. Isso também documenta: se o teste passa { status: 'arquivada' }, fica claro que o status é o que importa.

Capítulo 3Pirâmide, troféu e as duas escolas

Pergunta-gatilho

O que é uma "unidade" num teste unitário: uma função, uma classe ou outra coisa?

Ao final, você consegue
  • Diferenciar testes unitários, de integração, de ponta a ponta e de contrato.
  • Comparar a escola clássica e a londrina.
  • Escolher a proporção de cada tipo para cada projeto seu.

3.1 Os tipos

TipoO que exercitaVelocidadeExemplo seu
UnitárioUma unidade de comportamento, sem I/O de processo externomstelefone.test.ts do RH, cálculo de multa
IntegraçãoSeu código junto com o banco, a fila e o framework HTTP de verdade10–500 msduplicate.test.ts do marketZapp (pg_trgm real)
Ponta a ponta (E2E)O sistema inteiro pelo navegador (Playwright)segundos"candidato se inscreve e o recrutador vê"
ContratoSe o formato que você espera de um serviço externo continua igualmsFormato do evento da Evolution API

3.2 Pirâmide ou troféu?

A pirâmide clássica (Mike Cohn) diz: muitos unitários, alguns de integração, poucos E2E, porque unitários são rápidos e baratos. O troféu (Kent C. Dodds) diz: para aplicações web, a maior parte do valor está nos testes de integração, porque é na junção (SQL, serialização, middleware, permissão) que os bugs de verdade moram. Ferramentas como Testcontainers deixaram a integração rápida o bastante para isso.

Recomendação para os seus projetos

APIs CRUD com regras (RH, marketZapp, MesaPay, Julielton) se beneficiam do troféu: unitários para regras de cálculo puras, integração como base (rota HTTP + banco real) e 3 a 5 E2E só nos fluxos que dão dinheiro ou dor de cabeça. O pechincha (app Expo) é outro caso, com mais testes de componente.

3.3 As duas escolas

Clássica (Detroit)Londrina (mockista)
UnidadeUma unidade de comportamento, que pode envolver várias classesUma classe
IsolamentoIsola os testes uns dos outrosIsola a classe de todas as dependências
MocksSó para dependências compartilhadas ou fora do processoPara todo colaborador
RiscoUma falha pode apontar para várias classesTestes acoplados à implementação, que quebram em refatoração

Este material segue a escola clássica, como Khorikov, porque ela maximiza a resistência a refatoração. Na prática: mock é exceção, não regra.

Capítulo 4Dublês de teste: quando mockar

Pergunta-gatilho

O RH tem 14 arquivos de teste que mockam o Prisma. Que tipo de bug esses testes nunca vão pegar?

Ao final, você consegue
  • Nomear os cinco tipos de dublê.
  • Decidir quando mockar com a regra das dependências gerenciadas e não gerenciadas.
  • Usar vi.fn, vi.mock, monkeypatch e interfaces em Go.

4.1 Os cinco dublês (Meszaros)

DublêO que fazExemplo
DummyOcupa um parâmetro e nunca é usadonew Servico(null as any)
StubDevolve respostas prontas (entrada para o código testado)"a Evolution respondeu 200 com este JSON"
SpyRegistra as chamadas para verificar depoisvi.spyOn(email, 'enviar')
MockSpy com expectativa: verifica uma saída (efeito colateral)"enviou exatamente 1 mensagem para tal número"
FakeImplementação simplificada que funciona de verdadeRepositório em memória, servidor SMTP falso (Mailpit)

Regra de ouro: nunca verifique chamadas feitas a um stub. Se você deu ao código o dado X, conferir que ele "pediu X" é teste espelho: testa a implementação, não o resultado.

4.2 Quando mockar: dependências gerenciadas x não gerenciadas

O seu banco é um detalhe de implementação: ninguém além do seu sistema lê dele. Mockar o Prisma faz o teste verificar "o código chamou prisma.vaga.findMany com estes argumentos". Se o where estiver errado, por exemplo sem o filtro por empresa, o mock responde o que você mandou e o teste passa. Já a mensagem que vai para o WhatsApp de um cliente é observável de fora: ali o mock faz sentido, porque o contrato é "mandou esta mensagem para este número".

Caso real · RH

Os 34 testes do RH são ótimos para regras puras (telefone, schemas, roteiro.service) e para middleware de autenticação e RBAC. Os 14 que mockam o Prisma, porém, não protegem as consultas: filtros, joins, transações, unique, cascata. A missão M2 adiciona testes de integração com Postgres real para as consultas críticas, sem apagar os unitários.

Capítulo 5Integração com banco real

Pergunta-gatilho

Os testes do marketZapp leem o banco do .env. O que acontece se um dia esse .env apontar para produção?

Ao final, você consegue
  • Subir um Postgres descartável por suíte com Testcontainers ou docker compose.
  • Isolar os testes com transação revertida ou truncate.
  • Explicar por que SQLite no teste e Postgres em produção é um risco.

5.1 Três estratégias de banco para teste

EstratégiaPrósContras
Testcontainers: o teste sobe um container Postgres sozinhoZero configuração manual, mesma versão de produção, isolado, funciona igual no CIPrecisa de Docker. Sobe em ~2 a 5 s (uma vez por suíte)
Serviço no compose / no CI: um Postgres de teste fixo (TEST_DATABASE_URL)Simples. É o que o Julielton já suportaVocê precisa lembrar de subir. Risco de apontar para o banco errado
Banco em memória (SQLite) no lugar de PostgresRápido, sem DockerÉ outro banco: tipos, ILIKE, pg_trgm, JSONB, locks, fuso horário e constraints se comportam diferente
Caso real · Julielton e marketZapp

O conftest.py do Julielton usa SQLite por padrão e Postgres se TEST_DATABASE_URL existir. Bom desenho, mas o padrão deveria ser o banco de produção, e o CI deve rodar com Postgres. O marketZapp faz o certo ao testar o pg_trgm no Postgres real, mas carrega o banco do .env de desenvolvimento, o que mistura dados de teste com os seus e corre o risco de apontar para o lugar errado. A regra: teste usa um banco que só existe para teste, e a suíte se recusa a rodar se o nome do banco não terminar em _test.

5.2 Testcontainers no Vitest

export default async function setup() {
  const pg = await new PostgreSqlContainer('postgres:16-alpine').withDatabase('app_test').start();
  process.env.DATABASE_URL = pg.getConnectionUri();

  // marketZapp: aplicar db/schema.sql e CREATE EXTENSION pg_trgm

// vitest.config.ts → test: { globalSetup: ['./vitest.globalSetup.ts'] }

O globalSetup roda uma vez no processo principal, antes dos workers. A forma documentada de passar valores dele para os testes é provide('dbUrl', ...) no setup e inject('dbUrl') no teste. Alterar process.env no setup costuma funcionar, mas depende de como os workers são criados. Confira na documentação da sua versão do Vitest.

5.3 Isolamento entre testes

  • Transação revertida: cada teste abre uma transação e faz rollback no fim. É o mais rápido, mas não serve se o código testado abre a própria transação ou usa várias conexões.
  • Truncate de todas as tabelas no beforeEach: TRUNCATE ... RESTART IDENTITY CASCADE. Simples e robusto, custa alguns ms.
  • Banco por arquivo de teste (template database do Postgres): CREATE DATABASE t1 TEMPLATE app_template. Permite paralelismo total.

7.1 Tempo

Código que chama new Date() ou time.Now() por dentro é difícil de testar. Duas saídas:

  1. Injetar o relógio (a preferida): a função recebe agora como parâmetro, ou o serviço recebe um Relogio. Foi o que o exemplo do capítulo 1 fez com a multa.
  2. Relógio falso da ferramenta, quando não dá para mudar o código:

Erro comum: fuso horário

Testes que passam no seu notebook (America/Belem, UTC-3) e falham no CI (UTC). Fixe o fuso no ambiente de teste (TZ=UTC no script ou no workflow) e escreva as datas dos testes com fuso explícito. No banco, use timestamptz. O Julielton já trata isso em _data_com_fuso.

7.2 Aleatoriedade

Para lógica com muitas entradas possíveis, considere testes baseados em propriedades (fast-check, hypothesis, testing/quick e fuzzing nativo do Go), que geram centenas de entradas e encolhem o contraexemplo até o mínimo.

7.3 Filas (BullMQ) em dois níveis

  1. O processador como função pura: extraia a lógica do job para uma função processarAcao(dados, deps) e teste como qualquer unidade, sem Redis.
  2. Integração com Redis real (container): adicione o job com delay, avance o relógio e verifique o efeito. Teste também o que acontece quando o job falha: ele é reprocessado (attempts, backoff)? É idempotente se rodar duas vezes?

7.4 Concorrência

A regra "vale o último que salvou" do Julielton é um problema de concorrência, tema do Módulo 4. O teste que prova o problema é simples: disparar duas operações ao mesmo tempo e verificar o invariante.

Capítulo 8Cobertura, mutação e testes instáveis

Pergunta-gatilho

Escreva um teste que dê 100% de cobertura para uma função e mesmo assim não pegue nenhum bug.

Ao final, você consegue
  • Interpretar a cobertura de linha e de ramo e saber o que ela não diz.
  • Usar testes de mutação para medir a qualidade das asserções.
  • Diagnosticar e curar testes instáveis.

8.1 O que a cobertura diz e o que não diz

Cobertura mede quais linhas (ou ramos) foram executadas durante os testes, não quais foram verificadas. Um teste sem nenhum expect pode dar 100%. Por isso:

  • Cobertura baixa é um sinal útil: mostra código que nenhum teste toca.
  • Cobertura alta não prova nada sobre a qualidade dos testes.
  • Metas rígidas ("80% ou o CI falha") incentivam testes vazios. Prefira: "a cobertura do código novo não cai" e olhar o relatório nos módulos críticos.
  • Prefira cobertura de ramos: if (a && b) com um teste dá 100% de linha e 50% de ramos.
Como gerarnpx vitest run --coverage                 # npm i -D @vitest/coverage-v8
pytest --cov=mabsol_docs --cov-branch --cov-report=term-missing   # pip install pytest-cov
go test ./... -coverprofile=c.out && go tool cover -html=c.out

8.2 Testes de mutação: quem testa os testes

A ferramenta faz pequenas alterações no seu código (troca > por >=, + por -, apaga uma linha) e roda os testes. Se os testes continuarem passando, o mutante sobreviveu: você tem código executado mas não verificado. É a melhor medida da qualidade das asserções. Ferramentas: Stryker (JS/TS), mutmut (Python), Gremlins e go-mutesting (Go). É lento: rode em um módulo crítico por vez, como o cálculo de orçamento do Julielton, não no CI de todo push.

8.3 Testes instáveis (flaky)

Um teste que às vezes passa e às vezes falha sem mudança de código é pior que nenhum teste: ensina a equipe a apertar "rodar de novo". Causas e curas:

CausaCura
Tempo real, fuso, sleepRelógio injetado ou falso, TZ=UTC
Ordem entre testes / estado compartilhadoLimpar o estado por teste. Rodar em ordem aleatória para expor (vitest --sequence.shuffle, pytest-randomly, go test -shuffle=on)
Rede externa de verdadeMock na fronteira (capítulo 4)
Ordem de resultado sem ORDER BYOrdenar na consulta ou comparar sem ordem
Corrida com operação assíncronaawait no lugar certo. Esperar a condição, não um tempo fixo

Política: teste instável vai para a quarentena (marcado como skip com um link para uma issue) no mesmo dia, e é corrigido em até uma semana.

Capítulo 9TDD, regressão e código legado

Pergunta-gatilho

Quando a IA gera 200 linhas que "funcionam", como você se protege de quebrá-las na próxima mudança, sem entender cada linha de primeira?

Ao final, você consegue
  • Aplicar o ciclo vermelho-verde-refatorar.
  • Seguir a regra "todo bug vira teste antes da correção".
  • Escrever testes de caracterização para código que você não escreveu.

9.1 TDD em uma página

  1. Vermelho: escreva um teste para o próximo pedaço de comportamento. Rode e veja falhar, pelo motivo certo.
  2. Verde: escreva o mínimo de código para passar.
  3. Refatorar: melhore o código (e o teste) com a rede de segurança ligada.

Ver o teste falhar antes não é ritual: prova que o teste consegue falhar. Um teste que nunca foi visto vermelho pode estar testando nada. TDD funciona muito bem para regras de negócio bem definidas (RN-XX, cálculos) e menos para exploração de UI ou integração com uma API que você ainda não conhece.

9.2 Todo bug vira teste, antes da correção

  1. Reproduza o bug num teste automatizado. Ele deve falhar.
  2. Corrija o código. O teste passa.
  3. O teste fica para sempre e garante que o bug não volta.
Caso real · o marketZapp já faz isso

O whatsapp.test.ts documenta o incidente do webhook ("qualquer um podia forjar um messages.upsert... que foi o que aconteceu") e cobre até o detalhe sutil do apikey da Evolution que sombrearia o segredo. É o padrão a copiar: o comentário conta a história, e os testes impedem a repetição.

9.3 Testes de caracterização

Para código que funciona mas que você não entende totalmente (legado, ou gerado por IA), escreva testes que registram o comportamento atual, seja ele certo ou errado: chame com entradas variadas e fixe as saídas observadas. Agora você pode refatorar e entender com segurança. Quando descobrir que um comportamento está errado, mude o teste de propósito, num commit separado, explicando o porquê.

Fluxo com IA recomendado
  1. Você escreve (ou dita) os casos de teste, que são a especificação.
  2. A IA implementa.
  3. Você lê o diff e roda os testes.
  4. Peça à IA para atacar: "que entradas quebram esta função?". Cada resposta boa vira um caso novo.

Assim os testes são seus, mesmo que o código não seja.

10.1 O vocabulário

TermoSignificado

EventoO que dispara o workflow: push, pull_request, schedule (cron), workflow_dispatch (botão manual)

10.5 Tornar o CI obrigatório

Um CI que só avisa é ignorado na primeira pressa. Em Settings › Rules › Rulesets (ou Branch protection), crie uma regra para main: exigir pull request, exigir os status checks do workflow (selecione o job pelo nome) e bloquear push forçado. Sim, mesmo trabalhando sozinho: abrir PR para si mesmo dá um ponto de revisão do diff (regra da trilha) e garante o CI verde antes do merge.

10.6 Extras baratos e valiosos

  • Dependabot (.github/dependabot.yml): PRs automáticos de atualização de dependências e de actions. O CI testa cada um.
  • gitleaks no CI (Módulo 1, capítulo 9): uma action oficial do projeto roda a varredura a cada push.
  • npm audit --audit-level=high / pip-audit / govulncheck: vulnerabilidades conhecidas nas dependências.
  • Permissões mínimas: permissions: { contents: read } no topo do workflow. O token do Actions não precisa poder escrever no repositório para rodar testes.
Erro comum: pull_request_target

Esse evento roda com acesso aos segredos do repositório mesmo para PRs de forks. Combinado com um checkout do código do PR, permite que um estranho rode código com os seus segredos. Para CI de testes, use pull_request.

11.2 CD simples para a VPS

  1. No push para main, com testes verdes, o job de deploy constrói a imagem Docker e a publica no GitHub Container Registry (ghcr.io) com a tag do commit (sha).
  2. O job conecta por SSH na VPS (chave guardada em secrets, com um usuário só para deploy) e roda docker compose pull && docker compose up -d.
  3. Um smoke test chama /health. Se falhar, volta para a tag anterior.
  4. Use um environment production no GitHub com aprovação manual, se quiser um botão "aprovar deploy".

Rollback é a razão de usar a tag do commit e não latest: voltar é TAG=<sha-anterior> docker compose up -d. Migrações de banco complicam o rollback. O Módulo 4 trata de migrações compatíveis com a versão anterior.

Não precisa fazer tudo agora

A prioridade deste módulo é o CI. O CD automatizado só vale quando o CI está confiável. Até lá, o deploy manual documentado (como o deploy.md do marketZapp) é suficiente.

  • Postgres (e Redis) como serviço, com a mesma versão de produção
  • TZ=UTC e variáveis de teste explícitas

Apêndice AGabarito e revisão intercalada

Pré-teste

  1. Não. Cobertura mede o que foi executado, não o que foi verificado. (8.1)
  2. O stub fornece entrada (respostas prontas). O mock verifica saída (efeitos colaterais). (4.1)
  3. Em geral, não: é uma dependência gerenciada, então use o real em container e verifique o estado. (4.2)
  4. Está acoplado à implementação: falta resistência a refatoração, o que gera falsos positivos. (1.2)
  5. Teste que passa ou falha sem mudança de código. Causas: tempo/fuso, estado compartilhado, rede, ordem sem ORDER BY. (8.3)
  6. Injetar o relógio ou usar fake timers. (7.1)
  7. Workflow = arquivo. Job = conjunto de passos numa máquina. Step = um comando ou action. (10.1)
  8. Service container no workflow ou Testcontainers. (5.1, 10.2)
  9. Escrever um teste que reproduz o bug e vê-lo falhar. (9.2)
  10. Comportamento diferente: tipos, ILIKE, extensões, locks, fuso e constraints. (5.1)
  11. O merge na main exige o status check verde. Configura-se em Rulesets / Branch protection. (10.5)
  12. O de isolamento: protege contra vazamento de dados entre clientes, o risco mais caro, e exercita autenticação, rota e consulta juntos. (1.3, 6.2)

Capítulo 1

  1. Proteção contra regressão, resistência a refatoração, feedback rápido, manutenibilidade. A resistência a refatoração, porque falsos positivos destroem a confiança nos testes.
  2. Teste que falha sem haver bug. A equipe passa a ignorar falhas.
  3. Exemplo: permissões de admin (alto/alto), envio de candidatura (alto/médio), máscara de telefone (baixo/alto).
  4. R$ 199,99, R$ 200,00, R$ 200,01, mais um valor típico abaixo e um acima. Definir se "acima" inclui 200.

Capítulo 2

  1. Uma ação = um comportamento. Várias linhas indicam API ruim ou teste de vários comportamentos.
  2. Ex.: "recusa login com senha errada sem revelar se o e-mail existe".
  3. Reimplementa o código: se a lógica estiver errada nos dois lugares, o teste passa.
  4. Mostra o que importa no caso, porque só os campos relevantes aparecem, e absorve mudanças no modelo.

Capítulo 3

  1. Em apps web os bugs moram nas junções (SQL, HTTP, middleware), e containers deixaram a integração rápida.
  2. Uma unidade de comportamento, que pode envolver várias classes.
  3. Fixar exemplos reais do evento messages.upsert e validar que o parser os aceita, falhando se o formato mudar.

Capítulo 4

  1. Stub: dado entra no código testado. Mock: verifica o dado que sai para fora.
  2. É teste espelho: verifica implementação, não resultado.
  3. Gerenciadas: Postgres e Redis. Não gerenciadas: API da Anthropic e SMTP.
  4. where sem o filtro de empresa, unique violado, ordenação errada, transação incompleta.

Capítulo 5

  1. Tipos e coerção, ILIKE e extensões (pg_trgm), concorrência e locks, fuso horário, JSONB.
  2. Quando o código abre a própria transação ou usa várias conexões.
  3. Exigir um nome de banco terminando em _test e abortar caso contrário.

Capítulo 6

  1. Para testar via injeção, sem porta e sem efeitos colaterais.
  2. Ex.: /admin anônimo 302 para login, usuário comum 403, admin 200, /orcamentos/ID-de-outro 404, logout sem CSRF 400.
  3. Sem login, sessão expirada, corpo inválido, campo role extra, e-mail duplicado.

Capítulo 7

  1. Deixa a dependência explícita e funciona em qualquer ferramenta e linguagem.
  2. TZ=UTC no ambiente e datas com fuso explícito.
  3. Processador como função pura; integração com Redis real.
  4. Duas operações com Promise.allSettled e verificação do invariante (exatamente uma vence).

Capítulo 8

  1. Linhas executadas não são linhas verificadas.
  2. Uma alteração no código que nenhum teste detectou: falta asserção.
  3. Ver a tabela de 8.3.

Capítulo 9

  1. Prova que o teste é capaz de falhar, e pelo motivo certo.
  2. Teste que reproduz (vermelho) → correção (verde) → o teste fica para sempre.
  3. Teste que fixa o comportamento atual de código legado, para permitir refatorar com segurança.

Capítulo 10

  1. Jobs não compartilham arquivos (máquinas diferentes, a não ser via artifacts). Steps do mesmo job compartilham.
  2. Por localhost na porta mapeada (o job roda direto no runner).
  3. O primeiro é um valor descartável que só existe no CI. A chave de deploy dá acesso real.
  4. Cancelar execuções obsoletas do mesmo branch, economizando tempo e minutos.
  5. Ruleset/branch protection exigindo o status check.

Revisão intercalada

Para cada cenário: qual o problema e qual a correção?
  1. it('cria pedido', async () => { await criarPedido(dados); })
  2. Os testes passam localmente e falham no CI só entre 21h e 0h.
  3. O teste do serviço de vagas verifica expect(prisma.vaga.findMany).toHaveBeenCalledWith({...}).
  4. O CI leva 25 minutos, e a equipe passou a fazer merge sem esperar.
  5. O teste do lembrete usa await sleep(61_000).
  6. O workflow tem DATABASE_URL: ${{ secrets.PROD_DATABASE_URL }} no job de testes.
  7. Um bug de arredondamento no orçamento foi corrigido, sem teste novo.
  8. Os testes do Go passam, mas em produção aparece concurrent map writes.
  1. Sem asserção (cap. 2.4). Verificar o pedido gravado e o total.
  2. Fuso horário: em UTC já é o dia seguinte (cap. 7.1). Use TZ=UTC e datas explícitas.
  3. Teste espelho de dependência gerenciada (cap. 4.2). Use integração com banco real e verifique o resultado.
  4. Feedback lento (cap. 1.2 e 11). Paralelizar jobs, cache, mover E2E e mutação para um agendamento noturno.
  5. Tempo real no teste (cap. 7.1 e 8.3). Fake timers ou relógio injetado.
  6. Testes contra produção! (cap. 5.1). Use um service container, e o segredo de produção nunca no job de teste.
  7. Faltou o teste de regressão (cap. 9.2). Escrever o caso que reproduz o erro.
  8. Faltou go test -race e um teste concorrente (cap. 7.4 e 10.4).
