Capítulo 1Por que e o que testar

Pergunta-gatilho

Se você só pudesse escrever 5 testes no projeto do Julielton, quais seriam? Escreva os 5 títulos antes de continuar.

Ao final, você consegue
  • Explicar o valor de um teste em termos de custo do bug e de liberdade para mudar o código.
  • Priorizar o que testar com uma matriz de risco.
  • Transformar uma regra de negócio (RN) em casos de teste.

1.1 Para que servem os testes

A resposta comum é "achar bug". A resposta mais útil é: permitir mudar o código com segurança. Um projeto sem testes congela, porque toda mudança vira um risco que só aparece em produção. Com bons testes, você refatora, atualiza dependências e aceita código gerado por IA sabendo em segundos se algo quebrou. Testes também são documentação executável: o whatsapp.test.ts do marketZapp explica o contrato do webhook melhor que qualquer README, e nunca fica desatualizado, porque se ficar, quebra.

O custo de um bug cresce com a distância entre o momento em que ele nasce e o momento em que é descoberto: no editor, custa segundos; no CI, minutos; em produção, custa o tempo do cliente, a confiança e às vezes dados.

1.2 Os quatro pilares de um teste valioso (Khorikov)

PilarPergunta
Proteção contra regressãoSe alguém introduzir um bug aqui, o teste pega? Testes que executam mais código importante protegem mais.
Resistência a refatoraçãoSe eu reorganizar o código sem mudar o comportamento, o teste continua passando? Teste que quebra sem bug é falso positivo, e falsos positivos ensinam a equipe a ignorar os testes.
Feedback rápidoRoda em quanto tempo? Testes lentos deixam de ser rodados.
ManutenibilidadeÉ fácil de ler e de montar?

Os três primeiros competem entre si, e nenhum teste maximiza todos. Mas a resistência a refatoração não é negociável: um teste frágil tem valor negativo. É por isso que a regra é testar comportamento observável (o que a função devolve, o que a API responde, o que ficou gravado no banco) e não detalhes de implementação (qual método privado foi chamado, em que ordem).

1.3 O que testar primeiro: matriz de risco

Não tente cobrir tudo. Classifique cada funcionalidade por impacto se quebrar e probabilidade de quebrar (complexidade, frequência de mudança, histórico de bugs).

1.4 De regra de negócio para caso de teste

O REGRAS_DE_NEGOCIO.md do MesaPay, com códigos RN-XX, já é meio caminho andado. Para cada regra, escreva os casos com a técnica de partição e valor-limite: um caso típico de cada classe de entrada e os casos nas fronteiras.

Exemplo resolvido · uma RN fictícia no estilo do MesaPay

RN-XX: "A reserva pode ser cancelada sem multa até 2 horas antes do horário. Depois disso, cobra-se 20%. Reservas já iniciadas não podem ser canceladas."

  • Classes: mais de 2 h antes (sem multa), menos de 2 h (multa), já iniciada (erro).
  • Limites: exatamente 2 h antes ("até" inclui ou não? Pergunte ao cliente e registre na RN), 2 h menos 1 segundo, exatamente no horário.
  • Casos inválidos: reserva de outro estabelecimento, reserva já cancelada.

São 7 testes para uma regra de uma linha, e o caso de "exatamente 2 h" provavelmente revela uma ambiguidade que ninguém tinha decidido. Escrever o teste é uma forma de especificar.

Go · teste orientado por tabela (o padrão idiomático do MesaPay)func TestMultaCancelamento(t *testing.T) {
    inicio := time.Date(2026, 11, 20, 20, 0, 0, 0, time.UTC)
    casos := []struct {
        nome      string
        agora     time.Time
        multa     int // percentual
        erroEsper error
    }{
        {"3h antes, sem multa", inicio.Add(-3 * time.Hour), 0, nil},
        {"exatamente 2h antes, sem multa", inicio.Add(-2 * time.Hour), 0, nil},
        {"2h menos 1s, com multa", inicio.Add(-2*time.Hour + time.Second), 20, nil},
        {"já iniciada", inicio.Add(time.Minute), 0, ErrReservaIniciada},
    }
    for _, c := range casos {
        t.Run(c.nome, func(t *testing.T) {
            multa, err := MultaCancelamento(inicio, c.agora)
            if !errors.Is(err, c.erroEsper) { t.Fatalf("erro = %v, esperado %v", err, c.erroEsper) }
            if multa != c.multa { t.Errorf("multa = %d, esperado %d", multa, c.multa) }
        })
    }
}

Repare que o "agora" é parâmetro, não um time.Now() dentro da função. Isso torna a regra testável (capítulo 7).
