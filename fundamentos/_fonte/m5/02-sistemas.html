Capítulo 3Comunicação entre partes

Pergunta-gatilho

No MesaPay, a tela da cozinha precisa mostrar pedidos novos. Polling a cada 3 s com 40 estabelecimentos e 3 telas cada: quantas requisições por minuto? É muito?

Ao final, você consegue
  • Escolher entre comunicação síncrona e assíncrona.
  • Aplicar timeouts, retries com backoff e jitter, e circuit breaker.
  • Comparar polling, SSE e WebSocket para atualizações em tempo real.

3.1 Síncrona x assíncrona

Síncrona (HTTP request/response): quem chama espera a resposta. É simples e dá o resultado na hora, mas acopla a disponibilidade: se a Evolution está fora, a sua rota que chama a Evolution também falha. Assíncrona (fila, evento): quem chama registra o pedido e segue. É resiliente a falhas temporárias e absorve picos, mas o resultado vem depois, e você precisa lidar com reentrega e ordem (capítulos 4 e 5).

Regra prática: se o usuário precisa da resposta para continuar, use síncrono. Se é um efeito colateral (enviar mensagem, gerar PDF, notificar), use assíncrono.

3.2 Toda chamada de rede precisa de timeout

Sem timeout, uma dependência lenta prende conexões e memória até o seu app inteiro parar, o que é uma falha em cascata. O fetch do Node não tem timeout padrão.

Timeout + retry com backoff exponencial e jitterasync function chamarComRetry(url: string, init: RequestInit, tentativas = 3) {
  for (let i = 0; ; i++) {
    try {
      const r = await fetch(url, { ...init, signal: AbortSignal.timeout(5000) });   // 5 s
      if (r.status >= 500 || r.status === 429) throw new Error(`HTTP ${r.status}`); // só o que vale repetir
      return r;
    } catch (e) {
      if (i + 1 >= tentativas) throw e;
      const base = 500 * 2 ** i;                         // 0,5 s, 1 s, 2 s...
      await new Promise((ok) => setTimeout(ok, base / 2 + Math.random() * base / 2));  // jitter
    }
  }
}
  • Só repita o que é transitório: 5xx, 429, timeout, conexão recusada. Um 400 vai falhar de novo.
  • Só repita o que é idempotente, ou use uma chave de idempotência (capítulo 5). Repetir um POST que cobra pode cobrar duas vezes.
  • Jitter: sem ele, mil clientes que falharam juntos tentam de novo juntos, no mesmo milissegundo, e derrubam o serviço que estava voltando (efeito manada).
  • Circuit breaker: depois de N falhas seguidas, pare de chamar por um tempo e falhe na hora (ou use um plano B). Isso protege o seu app e dá fôlego para a dependência se recuperar. Em Node, a biblioteca opossum.

Resposta à pergunta-gatilho: 40 × 3 telas × 20 por minuto = 2.400 req/min, ou 40 req/s. Se cada uma é uma consulta indexada de 1 ms (Módulo 4), é carga trivial para uma VPS. Polling de 3 s é uma ótima decisão nesse contexto: simples, sem estado e fácil de depurar. Vale migrar para SSE quando a latência de 3 s incomodar o negócio ou o volume crescer 10×. Uma melhoria intermediária é o polling condicional: ETag/If-None-Match devolve 304 sem corpo quando nada mudou.

Capítulo 4Filas e trabalho em segundo plano

Pergunta-gatilho

O worker do marketZapp envia a mensagem no WhatsApp e, antes de marcar o job como concluído, o processo morre. O que acontece com esse job?

Ao final, você consegue
  • Explicar as garantias de entrega "no máximo uma vez" e "pelo menos uma vez".
  • Configurar tentativas, backoff, fila de mortos e detecção de jobs travados.
  • Comparar fila em Redis (BullMQ) e fila no Postgres.

4.1 Por que uma fila

O Julielton resume na primeira linha de tarefas.py: "O web só recebe e guarda; o trabalho pesado roda no worker." Isso dá: resposta rápida ao usuário, isolamento (OCR pesado não deixa o site lento), resiliência (se a dependência cai, a tarefa espera e tenta de novo), controle de vazão (o marketZapp espalha envios para não ser bloqueado pelo WhatsApp) e agendamento.

4.2 Garantias de entrega

GarantiaComoConsequência
No máximo uma vezMarca como feito antes de processarSe morrer no meio, o efeito nunca acontece
Pelo menos uma vezMarca como feito depois de processarSe morrer entre o efeito e a marcação, o job roda de novo. É o padrão do BullMQ e do tarefas.py
Exatamente uma vezNão existe de verdade entre sistemasO que existe é "pelo menos uma vez" + efeito idempotente = "efetivamente uma vez" (capítulo 5)

A resposta à pergunta-gatilho: o BullMQ detecta o job "travado" (stalled) e o devolve à fila, e a mensagem pode ser enviada duas vezes. O TRAVADA_APOS = 30 min do Julielton faz o mesmo papel. Por isso o processador precisa ser idempotente: o teste de 7.3 do Módulo 2.

4.3 A configuração que importa

  • Tentativas e backoff: o marketZapp usa attempts: 5 e backoff: exponential, 60 s, ou seja, esperas de cerca de 1, 2, 4 e 8 minutos. Adequado para uma API externa instável.
  • Fila de mortos (dead letter): o que esgotou as tentativas precisa ir para algum lugar visível e gerar alerta, não sumir. No BullMQ, os jobs com status failed: monitore a contagem. No tarefas.py, o status de erro com o traceback.
  • Erros permanentes x transitórios: número de WhatsApp inválido nunca vai funcionar. Não gaste 5 tentativas, marque como falha definitiva (no BullMQ, UnrecoverableError).
  • Desligamento gracioso: no SIGTERM (Módulo 3), pare de pegar jobs novos e termine o atual (worker.close()).
  • Retenção: o removeOnComplete: { count: 200 } do marketZapp evita que o Redis cresça sem limite.

BullMQ / Redis (marketZapp)Tabela + SKIP LOCKED (Julielton)

As duas escolhas foram boas para os seus contextos. O marketZapp precisa de agendamento por dias e de controle de taxa, e o BullMQ entrega isso pronto. O Julielton precisa de simplicidade e de consistência com o banco.

Capítulo 5Idempotência

Pergunta-gatilho

O cliente do MesaPay toca em "Pagar", a internet do celular oscila, ele não vê a confirmação e toca de novo. Quantas vezes ele foi cobrado?

Ao final, você consegue
  • Identificar operações que precisam ser idempotentes.
  • Implementar o padrão de chave de idempotência numa API.
  • Tornar consumidores de fila e de webhook idempotentes.

5.1 Definição

Uma operação é idempotente se executá-la várias vezes tem o mesmo efeito que executá-la uma vez. GET, PUT (substituir) e DELETE são idempotentes por definição do HTTP. POST (criar) não é. Em sistemas com rede, retries e filas, toda operação com efeito precisa ser idempotente, porque toda operação pode chegar mais de uma vez.

5.2 Chave de idempotência numa API

  1. O cliente gera um UUID por intenção ("este pagamento") e o envia no cabeçalho Idempotency-Key. Se tentar de novo, reenvia o mesmo UUID.
  2. O servidor grava a chave com uma restrição UNIQUE, na mesma transação do efeito.
  3. Se a chave já existe, devolve a resposta guardada, sem executar de novo.
Esqueleto em Go + GORM (MesaPay)type ChaveIdempotencia struct {
    Chave      string `gorm:"primaryKey"`
    UsuarioID  uint   // a chave vale por usuário: evita colisão e abuso
    Status     int
    Resposta   []byte
    CriadoEm   time.Time
}

func (h *Handler) Pagar(ctx *gin.Context) {
    chave := ctx.GetHeader("Idempotency-Key")
    if chave == "" { ctx.JSON(400, gin.H{"erro": "Idempotency-Key obrigatório"}); return }
    var anterior ChaveIdempotencia
    if h.db.First(&anterior, "chave = ? AND usuario_id = ?", chave, usuarioID(ctx)).Error == nil {
        ctx.Data(anterior.Status, "application/json", anterior.Resposta)   // repete a resposta
        return
    }
    err := h.db.Transaction(func(tx *gorm.DB) error {
        pag, err := h.svc.RegistrarPagamento(tx, ...)
        if err != nil { return err }
        corpo, _ := json.Marshal(pag)
        return tx.Create(&ChaveIdempotencia{Chave: chave, UsuarioID: usuarioID(ctx), Status: 201, Resposta: corpo}).Error
        // duas requisições simultâneas com a mesma chave: a segunda viola a PK e faz ROLLBACK
    })
    ...
}

Expire as chaves depois de 24 a 48 h. Rejeite a mesma chave com um corpo diferente (422): é um bug do cliente.

5.3 Consumidores idempotentes

  • Tabela de processados: INSERT INTO evento_processado (id) ... ON CONFLICT DO NOTHING RETURNING id. Se não voltou nada, já foi processado (Módulo 4, 2.1).
  • Operação naturalmente idempotente: UPDATE pedido SET status = 'pronto' WHERE id = 7 pode rodar 10 vezes. UPDATE estoque SET qtd = qtd - 1 não pode.
  • Efeito externo: se a API externa aceita uma chave de idempotência (Stripe e muitos gateways de pagamento aceitam), repasse o ID do job. Se não aceita (envio de WhatsApp), registre "enviado" logo após o sucesso e confira antes de enviar. Sobra uma janela pequena, que é aceitável para mensagem e inaceitável para dinheiro.

Capítulo 6Consistência entre sistemas e outbox

Pergunta-gatilho

O código faz await db.anuncio.create(...) e depois await fila.add('publicar', ...). Liste o que pode dar errado entre essas duas linhas.

Ao final, você consegue
  • Explicar o problema da escrita dupla.
  • Implementar o padrão outbox.
  • Descrever consistência eventual e sagas sem jargão.

6.1 O problema da escrita dupla

Gravar em dois sistemas (banco + fila, banco + e-mail, banco + API externa) não é atômico. Na pergunta-gatilho: o processo pode morrer entre as duas linhas (anúncio criado, nunca publicado), o Redis pode estar fora (idem), ou, se inverter a ordem, o job pode rodar antes do commit e não achar o anúncio, ou achar um anúncio que depois sofreu rollback.

6.2 Padrão outbox

  1. Na mesma transação do dado, grave uma linha na tabela outbox com o evento (tipo, payload, criado_em, enviado_em NULL).
  2. Um relay (um loop no worker) lê os pendentes com FOR UPDATE SKIP LOCKED, publica na fila ou chama a API, e marca enviado_em.
  3. Se o relay morrer entre publicar e marcar, publica de novo: pelo menos uma vez, então o consumidor precisa ser idempotente (capítulo 5). As peças se encaixam.

Repare: a fila no Postgres do Julielton já é, na prática, um outbox, porque a tarefa nasce na mesma transação que o dado. Com BullMQ, o outbox é a ponte que falta entre o banco e o Redis.

6.3 Consistência eventual e sagas

Consistência eventual: depois de uma mudança, as partes do sistema vão concordar em algum momento, e não instantaneamente. A contagem de candidatos no painel pode estar 2 segundos atrasada. Isso é aceitável quando o negócio tolera, e precisa ser uma decisão explícita.

Saga: uma operação de negócio que atravessa vários sistemas como uma sequência de passos locais, cada um com uma ação de compensação se algo der errado depois. Exemplo: reservar mesa → cobrar sinal → confirmar. Se a cobrança falha, a compensação é liberar a mesa. Não existe rollback entre sistemas, só compensação.

Sobre o teorema CAP

Você vai ouvir "CAP: escolha 2 de 3". A versão útil é: quando a rede entre partes falha, você escolhe entre responder (com dado possivelmente desatualizado) ou recusar (para não mostrar dado errado). Com um banco só numa VPS, esse dilema praticamente não aparece. Ele surge quando há réplicas ou sistemas separados.
