Capítulo 1Modelagem e restrições

Pergunta-gatilho

Ao final, você consegue

1.2 Restrições: a aplicação valida, o banco garante

A validação na aplicação dá mensagens amigáveis. A restrição no banco garante, inclusive contra: duas requisições simultâneas (as duas verificam "não existe" e as duas inserem), um script manual, outra aplicação lendo o mesmo banco, ou um bug. A resposta da pergunta-gatilho é concorrência: check-then-insert na aplicação tem uma janela em que as duas requisições passam.

SQL · as restrições essenciaisCREATE TABLE reserva (
  id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  estabelecimento_id bigint NOT NULL REFERENCES estabelecimento(id),
  mesa_id          bigint NOT NULL REFERENCES mesa(id),
  inicio           timestamptz NOT NULL,
  pessoas          int NOT NULL CHECK (pessoas BETWEEN 1 AND 50),
  valor_sinal      numeric(10,2) NOT NULL DEFAULT 0 CHECK (valor_sinal >= 0),
  status           text NOT NULL DEFAULT 'ativa' CHECK (status IN ('ativa','cancelada','concluida')),
  criado_em        timestamptz NOT NULL DEFAULT now()
);
-- uma reserva ativa por mesa e horário:
CREATE UNIQUE INDEX reserva_mesa_horario ON reserva (mesa_id, inicio) WHERE status = 'ativa';

1.3 Exemplo resolvido: o índice parcial do MesaPay

Caso real · models/indices.go 
CREATE UNIQUE INDEX IF NOT EXISTS idx_mesa_restaurante_numero
  ON mesas (restaurante_id, numero)
  WHERE deleted_at IS NULL

Três decisões num comando só: (1) o número da mesa é único por estabelecimento (composto), e não no sistema todo; (2) só entre as mesas não excluídas (parcial), senão uma mesa apagada com soft delete ocuparia o número para sempre; (3) no índice de usuários, username IS NOT NULL aproveita que NULL não colide com NULL. O comentário no código explica cada uma. É exatamente assim que se faz.

1.4 Soft delete: cuidados

Marcar deleted_at em vez de apagar preserva histórico, mas: toda consulta precisa lembrar o filtro (o GORM faz isso automaticamente, o SQL puro não), índices únicos precisam ser parciais (1.3), chaves estrangeiras continuam apontando para linhas "mortas", e a LGPD pode exigir apagar de verdade os dados pessoais. Alternativa: mover para uma tabela de arquivo, ou anonimizar.

1.5 Normalização na medida

Normalizar (até a 3ª forma normal) é guardar cada fato em um lugar só: o nome do cliente fica na tabela de clientes, e não copiado em cada pedido. Isso evita inconsistência quando o dado muda. Desnormalize de propósito quando o dado é um registro histórico: o preço no momento da venda deve ser copiado para o item do pedido, porque o preço do produto vai mudar e o pedido antigo não pode mudar junto.

Capítulo 2SQL além do CRUD

Pergunta-gatilho

Quantas consultas o ORM faz para listar 50 vagas com o número de candidatos de cada uma?

Ao final, você consegue
  • Escrever agregações, CTEs, funções de janela e upserts.
  • Identificar e corrigir o problema N+1 nos três ORMs.

2.1 O kit que resolve 90% dos relatórios

Agregação com filtro, CTE e função de janelaWITH por_vaga AS (
  SELECT v.id, v.titulo,
         count(c.id)                                        AS candidatos,
         count(c.id) FILTER (WHERE c.status = 'aprovado')   AS aprovados
  FROM vaga v
  LEFT JOIN candidatura c ON c.vaga_id = v.id
  WHERE v.empresa_id = $1
  GROUP BY v.id, v.titulo
)
SELECT *,
       rank() OVER (ORDER BY candidatos DESC) AS posicao   -- ranking sem perder as linhas
FROM por_vaga
ORDER BY candidatos DESC
LIMIT 50;
  • LEFT JOIN mantém as vagas sem candidatos (o INNER as descartaria).
  • FILTER (WHERE ...) conta subconjuntos sem precisar de subconsulta.
  • Funções de janela (rank, row_number, sum() OVER, lag) calculam sobre um grupo sem agrupar as linhas.
Upsert e RETURNINGINSERT INTO evento_processado (evento_id, processado_em)
VALUES ($1, now())
ON CONFLICT (evento_id) DO NOTHING
RETURNING evento_id;          -- vazio se já existia: idempotência do webhook (Módulo 1, cap. 8)

2.2 O problema N+1

Buscar uma lista (1 consulta) e, para cada item, buscar o relacionado (N consultas). Com 50 vagas, são 51 idas ao banco. O pior é que funciona bem no seu notebook com 5 linhas e fica lento em produção.

Errado · Prismaconst vagas = await prisma.vaga.findMany({ where: { empresaId } });
for (const v of vagas) v.total = await prisma.candidatura.count({ where: { vagaId: v.id } });
Certo · nos três ORMs// Prisma: contagem de relação numa consulta só
prisma.vaga.findMany({ where: { empresaId }, include: { _count: { select: { candidaturas: true } } } });

# SQLAlchemy 2: carregar a relação em lote
select(Projeto).options(selectinload(Projeto.documentos)).where(Projeto.cliente_id == cid)

// GORM: Preload faz uma consulta extra por relação, não uma por linha
db.Preload("Itens").Where("estabelecimento_id = ?", id).Find(&comandas)

Como descobrir: ligue o log de consultas em desenvolvimento (Prisma log: ['query'], SQLAlchemy echo=True, GORM Logger.LogMode(logger.Info)) e conte as linhas por requisição.
