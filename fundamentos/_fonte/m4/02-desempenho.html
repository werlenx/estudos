Capítulo 3Índices

Pergunta-gatilho

Se índice deixa a consulta rápida, por que não criar um índice em cada coluna?

Ao final, você consegue
  • Explicar como uma árvore B encontra uma linha.
  • Definir a ordem das colunas de um índice composto.
  • Escolher entre índice B-tree, parcial, de expressão, GIN e covering.

3.1 Como um índice B-tree funciona

Imagine a lista telefônica: ordenada por sobrenome e nome, você acha "Silva, Maria" sem ler tudo. O índice B-tree é uma estrutura ordenada pelos valores das colunas, com ponteiros para as linhas. Ele acha um valor em poucos passos (logarítmico), e também serve para intervalos (BETWEEN, >) e para ordenar (ORDER BY) sem ordenação extra.

A mesma lista telefônica explica a regra mais importante: ela não ajuda a achar todas as "Marias" se você não sabe o sobrenome. É a regra do prefixo à esquerda.

3.2 Índice composto: a ordem importa

Índice em (estabelecimento_id, criado_em)Usa o índice?
WHERE estabelecimento_id = 7Sim (prefixo)
WHERE estabelecimento_id = 7 AND criado_em > now() - '7 days'Sim, e muito bem: igualdade primeiro, intervalo depois
WHERE estabelecimento_id = 7 ORDER BY criado_em DESC LIMIT 20Sim, e sem ordenar: lê as 20 primeiras do índice
WHERE criado_em > now() - '7 days'Em geral, não de forma eficiente (falta o prefixo)

Regra prática: colunas comparadas por igualdade primeiro, depois a de intervalo ou ordenação. Em sistemas multi-tenant, o tenant_id quase sempre vai na frente, porque toda consulta filtra por ele (Módulo 1, capítulo 4).

3.3 Tipos de índice que você vai usar

TipoExemploPara quê
Parcial... WHERE deleted_at IS NULLIndexar só as linhas consultadas. Menor e mais rápido (MesaPay)
De expressãoCREATE INDEX ON usuario (lower(email))Busca sem diferenciar maiúsculas. A consulta precisa usar a mesma expressão
CoveringCREATE INDEX ON pedido (cliente_id) INCLUDE (total)Permite Index Only Scan, sem ler a tabela
GIN + pg_trgmCREATE INDEX ON anuncio USING gin (titulo gin_trgm_ops)ILIKE '%texto%' e similaridade (o caso do marketZapp)
GIN em jsonbUSING gin (dados jsonb_path_ops)Consultas @> em documentos

3.4 O custo dos índices

Cada índice é uma estrutura a mais para atualizar em todo INSERT, UPDATE de coluna indexada e DELETE. Ele também ocupa disco e memória de cache. Índice que nenhuma consulta usa é só custo. Para encontrá-los:

SELECT relname AS tabela, indexrelname AS indice, idx_scan AS usos,
       pg_size_pretty(pg_relation_size(indexrelid)) AS tamanho
FROM pg_stat_user_indexes ORDER BY idx_scan ASC LIMIT 20;

Chaves estrangeiras não ganham índice automático no Postgres. Indexe a coluna FK do lado "muitos" (candidatura.vaga_id), senão os joins e o DELETE do pai ficam lentos.

Capítulo 4Lendo o EXPLAIN ANALYZE

Pergunta-gatilho

Uma consulta leva 2 segundos em produção e 5 ms no seu notebook. Qual a primeira coisa que você faz?

Ao final, você consegue
  • Ler um plano de execução e achar o nó caro.
  • Diagnosticar estimativas erradas e falta de índice.
  • Encontrar as consultas mais caras do sistema com pg_stat_statements.

4.1 Exemplo resolvido

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM comanda WHERE estabelecimento_id = 7 AND status = 'aberta' ORDER BY aberta_em DESC LIMIT 20;

Limit  (cost=0.00..4210.33 rows=20 width=96) (actual time=0.03..812.40 rows=20 loops=1)
  ->  Sort  (actual time=812.38..812.39 rows=20 loops=1)
        Sort Key: aberta_em DESC
        ->  Seq Scan on comanda  (cost=0.00..4100.00 rows=150 width=96)
                                  (actual time=0.02..809.10 rows=1840 loops=1)
              Filter: ((estabelecimento_id = 7) AND (status = 'aberta'))
              Rows Removed by Filter: 498160
  Buffers: shared read=3100
Planning Time: 0.2 ms
Execution Time: 812.5 ms

Leitura, de dentro para fora (o nó mais indentado roda primeiro):

  1. Seq Scan: leu a tabela inteira (500 mil linhas) e descartou 498.160 (Rows Removed by Filter). Esse é o nó caro.
  2. Estimativa errada: esperava 150 linhas (rows=150) e vieram 1.840. Estimativas muito erradas levam a planos ruins. Rode ANALYZE comanda para atualizar as estatísticas.
  3. Sort depois do filtro: precisou ordenar porque nenhum índice entrega aberta_em já ordenado.
  4. shared read=3100: 3.100 blocos lidos do disco (não estavam em cache).
CorreçãoCREATE INDEX CONCURRENTLY comanda_estab_status_aberta
  ON comanda (estabelecimento_id, status, aberta_em DESC);

-- novo plano:
Limit  (actual time=0.04..0.09 rows=20 loops=1)
  ->  Index Scan using comanda_estab_status_aberta on comanda (actual rows=20 loops=1)
        Index Cond: ((estabelecimento_id = 7) AND (status = 'aberta'))
Execution Time: 0.12 ms

De 812 ms para 0,12 ms: igualdade primeiro, ordenação depois, e o LIMIT para de ler após 20 linhas.

4.2 Glossário dos nós

NóSignifica
Seq ScanLeitura da tabela inteira. Normal em tabelas pequenas ou quando a maioria das linhas é retornada
Index ScanPercorre o índice e busca cada linha na tabela
Index Only ScanResponde só com o índice (covering). O mais rápido
Bitmap Heap ScanJunta vários resultados de índice e lê a tabela em ordem física. Bom para volumes médios
Nested LoopPara cada linha de um lado, procura no outro. Ótimo se um lado é pequeno e o outro indexado
Hash JoinMonta uma tabela hash de um lado. Bom para junções grandes sem ordem
Sort / "external merge Disk"Ordenação. "Disk" indica que não coube no work_mem
Erro comum

Testar desempenho com 50 linhas. Com tabela pequena o Postgres prefere Seq Scan, e com razão. Gere volume realista para testar: INSERT ... SELECT FROM generate_series(1, 500000). E cuidado: EXPLAIN ANALYZE executa a consulta. Num UPDATE ou DELETE, use dentro de BEGIN; ... ROLLBACK;.

4.3 Achar as consultas que importam: pg_stat_statements

-- habilitar: shared_preload_libraries = 'pg_stat_statements' (no compose: command: postgres -c shared_preload_libraries=pg_stat_statements)
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT round(total_exec_time) AS ms_total, calls, round(mean_exec_time,1) AS ms_media,
       left(query, 80) AS consulta
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

Otimize pelo tempo total (média × chamadas), não pela consulta mais lenta: uma de 5 ms chamada um milhão de vezes pesa mais que uma de 2 s chamada uma vez por dia.

Capítulo 5Transações e ACID

Pergunta-gatilho

Um pagamento é registrado e, na linha seguinte, a atualização da comanda falha. O que fica gravado no banco?

Ao final, você consegue
  • Explicar as quatro garantias ACID.
  • Usar transações no Prisma, no SQLAlchemy e no GORM.
  • Evitar os erros que deixam transações longas ou abertas.

5.1 ACID

LetraGarantia
AtomicidadeTudo ou nada. Se algo falha no meio, nada fica gravado. (A resposta da pergunta-gatilho, se as duas operações estiverem na mesma transação.)
ConsistênciaA transação leva o banco de um estado válido a outro: as restrições valem no fim.
IsolamentoTransações simultâneas não se atrapalham... até certo ponto, que é o capítulo 6.
DurabilidadeDepois do COMMIT, sobrevive a queda de energia (graças ao WAL).

5.2 Nas suas ferramentas

Prisma (RH): transação interativaawait prisma.$transaction(async (tx) => {
  const pag = await tx.pagamento.create({ data: { comandaId, valor } });
  await tx.comanda.update({ where: { id: comandaId }, data: { status: 'paga' } });
  return pag;
}, { timeout: 5000 });          // se qualquer linha lançar erro, ROLLBACK de tudo
SQLAlchemy 2 (Julielton)with Session(engine) as s, s.begin():     # COMMIT ao sair; ROLLBACK se houver exceção
    s.add(Pagamento(comanda_id=cid, valor=v))
    s.get(Comanda, cid).status = "paga"
GORM (MesaPay)err := db.Transaction(func(tx *gorm.DB) error {
    if err := tx.Create(&pagamento).Error; err != nil { return err }       // erro → ROLLBACK
    return tx.Model(&Comanda{}).Where("id = ?", id).Update("status", "paga").Error
})
Três erros clássicos
  • Usar o cliente global dentro da transação: no Prisma, chamar prisma.x em vez de tx.x dentro do $transaction executa fora da transação. No GORM, o mesmo com db em vez de tx.
  • Chamada externa dentro da transação (Evolution, e-mail, Anthropic): a transação fica aberta segurando locks enquanto a rede demora. E se a chamada externa der certo e o COMMIT falhar, a mensagem foi enviada para algo que não existe. Faça o externo depois do commit, de preferência via fila (padrão outbox, Módulo 5).
  • Transação esquecida aberta (idle in transaction): segura locks e impede o vacuum. Configure idle_in_transaction_session_timeout (capítulo 9).

Capítulo 6Isolamento e anomalias

Pergunta-gatilho

Duas transações leem o saldo (R$ 100), cada uma subtrai R$ 30 e grava. Qual o saldo final? Qual deveria ser?

Ao final, você consegue
  • Nomear e reproduzir as anomalias de concorrência.
  • Prever o que cada nível de isolamento do Postgres impede.
  • Tratar erros de serialização com retry.

6.1 As anomalias

AnomaliaO que acontece
Leitura sujaLer dado não confirmado de outra transação. O Postgres nunca permite.
Leitura não repetívelLer a mesma linha duas vezes na transação e obter valores diferentes
FantasmaRepetir uma consulta com WHERE e aparecerem linhas novas
Atualização perdida (lost update)Duas transações leem, calculam e gravam: a segunda sobrescreve a primeira (a pergunta-gatilho: o saldo final fica 70 em vez de 40)
Write skewDuas transações leem o mesmo conjunto, decidem com base nele e gravam linhas diferentes, quebrando uma regra (ex.: "pelo menos um gerente de plantão", e os dois saem ao mesmo tempo)

6.2 Os níveis no Postgres

NívelComo funcionaLost update / write skew
Read Committed (padrão)Cada comando vê o que estava confirmado quando ele começouLost update acontece no padrão "ler → calcular na aplicação → gravar"
Repeatable ReadA transação inteira vê um retrato (snapshot) do inícioLost update vira erro 40001 (precisa de retry). Write skew ainda passa
SerializableGarante resultado equivalente a alguma execução em série (SSI)Ambos viram erro 40001. Exige retry sempre

6.3 Reproduza com dois terminais

-- preparação:  CREATE TABLE conta (id int PRIMARY KEY, saldo numeric); INSERT INTO conta VALUES (1, 100);
-- Terminal A                              -- Terminal B
BEGIN;                                     BEGIN;
SELECT saldo FROM conta WHERE id=1; -- 100
                                           SELECT saldo FROM conta WHERE id=1; -- 100
UPDATE conta SET saldo = 70 WHERE id=1;    -- (a aplicação calculou 100 - 30)
COMMIT;
                                           UPDATE conta SET saldo = 70 WHERE id=1;  -- também calculou 100 - 30
                                           COMMIT;
SELECT saldo FROM conta;  -- 70   ← os R$ 30 da transação A sumiram

Agora repita com BEGIN ISOLATION LEVEL REPEATABLE READ; nos dois terminais: o UPDATE do B falha com could not serialize access due to concurrent update. Por fim, repita no Read Committed, mas escrevendo SET saldo = saldo - 30: o resultado fica correto (40), porque o cálculo foi para dentro do banco (capítulo 7).

Retry de erro de serialização (TypeScript, genérico)async function comRetry<T>(fn: () => Promise<T>, tentativas = 3): Promise<T> {
  for (let i = 1; ; i++) {
    try { return await fn(); }
    catch (e: any) {
      const serializacao = e?.code === '40001' || e?.code === '40P01';   // serialização / deadlock
      if (!serializacao || i >= tentativas) throw e;
      await new Promise((r) => setTimeout(r, 20 * i + Math.random() * 30));  // backoff com jitter
    }
  }
}
// no Prisma, o erro chega embrulhado (P2034 para conflito de transação); confira o código no erro real

7.3 Fila no Postgres com SKIP LOCKED

Vários workers pegando tarefas sem pegar a mesmaWITH proxima AS (
  SELECT id FROM tarefa
  WHERE status = 'pendente' AND executar_em <= now()
  ORDER BY executar_em
  FOR UPDATE SKIP LOCKED          -- pula as linhas que outro worker já travou
  LIMIT 10
)
UPDATE tarefa SET status = 'processando', inicio = now()
FROM proxima WHERE tarefa.id = proxima.id
RETURNING tarefa.*;

Para volumes pequenos e médios, isso dispensa o Redis. O Julielton já faz exatamente isso em src/mabsol_docs/tarefas.py: o web só grava a tarefa, e o worker reserva com FOR UPDATE SKIP LOCKED, com tentativas máximas e devolução das tarefas travadas há mais de 30 minutos. Leia o arquivo com este capítulo ao lado. O marketZapp usa BullMQ (Redis), que também é uma boa escolha. O Módulo 5 compara os dois.

7.4 Deadlocks

A transação A trava a linha 1 e quer a 2. A B trava a 2 e quer a 1. O Postgres detecta, mata uma delas (erro 40P01) e a outra segue. Prevenção: sempre travar na mesma ordem (por exemplo, ordenar os IDs antes de atualizar vários registros), manter as transações curtas, e fazer retry do erro.
